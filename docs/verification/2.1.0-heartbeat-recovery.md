# 2.1.0 heartbeat recovery candidate

Development base: `c2a3d5c308da73ca868bec596291a3d69f6b8be4` (the retained
2.0.6 diagnostics). Production main remains the 2.0.8 backend rollback. This
change targets develop only; no mobile build, release tag, main merge or

must assign the platform build number when a binary is actually built.

## Evidence and limits

Read-only production observations on 2026-11-03 around 18:58–18:59 KST showed
one Android 2.0.5+79 TV with a heartbeat timestamp frozen at 18:03:30 while its
`preparationHealth` continued receiving server timestamps, stage `heartbeat`,
code `unexpected`, and repeated attempts. The other two TVs were fresh. The
18:31:55 class start selected those other two TVs. This establishes a heartbeat
failure with continuing writes, not its initial cause or actual screen playback.

The incident's original native exception/stack was not available in the queried
Cloud Logging/Crashlytics results. Do not equate the following reproductions
with proof of what first happened on that physical TV.

Two failures are independently reproducible:

1. A caller's timeout does not cancel its SDK Future. Before this change, four
   retries could leave four original writes outstanding. The candidate retains
   the actual Future across retries and datasource/hook reconstruction. Equal
   intents join it; ready ACKs and different connections serialize separately.
2. With the real FlutterFire web SDK and a local RTDB emulator, a child health
   `set` rejects a pending device transaction. The web adapter reports `unknown`
   for that SDK error; Android's installed adapter uses `overridden-by-set`.
   The candidate uses a device transaction for health instead. The same SDK
   probe also exposed error clearing that silently aborted on empty child cache.
   The candidate permits server retry of the initial empty device cache.

## Behavior

- Heartbeat identity/paired/connection/policy/offline guards remain enforced.
  Local rejection now preserves a specific `heartbeat_*` reason in the original
  diagnostic and uses existing `failed-precondition` on the wire.
- Known native transaction/transport errors map to existing collector/rules
  codes (`aborted`, `unavailable`, `unauthenticated`, `cancelled`). Full original
  Firebase codes remain in detailed diagnostics. Truly unknown errors remain
  unknown rather than being assigned a speculative cause.
- Health transactions cannot recreate a removed registration or overwrite a
  newer connection when a connection fence is supplied. Heartbeat success does
  not clear media/response failures. The hook supplies its connection fence.
- After two failed periodic heartbeat cycles, confirmed standby can request the
  existing transport recovery. Playing/paused sessions, unknown session state,
  changed owner and permission denial do not trigger automatic transport reset.
  Recovery is limited to one attempt per two minutes and three attempts until a
  successful heartbeat. Connection changes do not reset that budget. A recovery
  request/return is not reported as heartbeat success.
- Native heartbeat diagnostics use the 2.0.6 bounded remote diagnostic queue;
  context now distinguishes periodic work and includes attempt/elapsed time.
  Existing installed 2.0.5 apps do not gain these changes from a server deploy.

No Functions or database rules change is introduced by this patch. Wire codes
and health fields are already supported by the restored production collector.
The pre-existing develop/main collector differences remain separate. Release
compatibility checks are still required when later promoting/building.
