# 2.0.6 preparation diagnostics

The StationD tablet sometimes times out after eight seconds while publishing a
preparation request. Existing records contain both isolated and overlapping
failures. The origin of the delay is not established; this patch adds evidence
without claiming that overlap, Wi-Fi, or device hardware is the root cause.

## Behavior

- Keep the eight-second UI deadline, readiness rules, playback commands, and
  request/receipt wire formats. Diagnostics never reconnect the SDK or retry a
  preparation write.
- Add an optional, strictly allowlisted `trace` to existing operation telemetry:
  ephemeral preparation ID, target count/index, pending write count, observed
  RTDB connection state/change age, and app lifecycle state/change age.
- Observe the original write after the UI timeout. A separate
  `tv.prepare.settlement` event links to the original operation and records late
  success/failure, elapsed time and whether the UI request was superseded. It
  never turns the original failed attempt into a successful user action.
- On timeout only, perform a read-only HTTPS probe of
  `displayPreparation/request/sessionId`. It has a two-second auth deadline,
  three-second HTTP deadline, six-second outer deadline, one in-flight probe,
  and at most one probe per minute per account observation scope. No product
  action awaits it. Account change/disposal suppresses stale results.
- TV media preparation logs the same request ID and target index, with elapsed
  media, response-write and heartbeat time. Native handled preparation errors
  also use the existing bounded remote diagnostic queue without waiting for a
  Crashlytics upload/relaunch.
- Retain `prepare_request` / `prepare_receipts` outcome codes; the added
  `transportCode` records timeout/permission/etc. without changing existing
  report classifications.
- Reject content, tokens, URLs, SSIDs, IPs and arbitrary identifiers from the new
  trace. Existing account-scoped queues remain bounded (24-hour TTL; 128
  operation events / 30 detailed errors). Diagnostics are best-effort, not a
  durable audit trail. App termination can prevent a late completion record.

## How to investigate the next failure

Query `recordoperationtelemetry` Cloud Run logs for
`jsonPayload.action="tv.prepare.request"`, outcome failure, then use
`jsonPayload.trace.requestId` to join tablet, probe, settlement and TV events.
Use `trace.parentOperationId` for the exact originating attempt.

| Evidence | Interpretation and limit |
| --- | --- |
| Write times out; HTTPS probe succeeds with `requestMatch=same` | That request existed on the server when the probe read it. Investigate delayed SDK acknowledgement/processing; this does not establish its original arrival time. |
| Late settlement succeeds after eight seconds | The UI timed out before the underlying SDK Future completed. Do not count this as a second user incident or change the original outcome. |
| HTTPS succeeds with `different` / `absent` | Only the state at probe time is known; another selection/retry may have replaced the request. It does not prove that the original write never arrived. |
| Probe times out in `auth` | Token retrieval/refresh delayed; no HTTP probe result exists. |
| Probe times out in `http` and write also times out | Both transports to RTDB were delayed. Device/network/backend-path investigation is still needed; this alone does not identify Wi-Fi. |
| Write succeeds; TV preparation fails | Use target index, stage and remote error context to distinguish media preparation, response publication and heartbeat. |
| Multiple requests with nonzero pending writes | Requests overlapped. This does not prove overlap caused the first delay. |

`.info/connected` is an SDK observation, not an independent Internet health test.
`connectionAgeMs` is time since the last observed state change, not a heartbeat
round-trip measurement. `observerAgeMs` starts when this account's diagnostic
observer is created, not at tablet power-on. Wall clocks differ between devices;
use operation elapsed times and IDs rather than inferring millisecond causal
ordering across devices.

## Compatibility and rollout

Deploy the additive collector before distributing the app. It continues to
accept unchanged 2.0.5 payloads. If the collector is rolled back, the new app
retries an invalid-argument response once without `trace` for existing actions;
new diagnostic-only actions may be discarded by the old collector. Class data
and control do not depend on either collector version.

2.0.5 tablets/TVs and 2.0.6 tablets/TVs use the same preparation and playback
protocols. Older TVs have less diagnostic detail; updating the tablet alone does
not retrofit new trace fields into those TVs. No minimum-version change is part
of this patch.

Verification uses the released source
`5d3a601e88d8ecc921fb41f9b12b698d6caa82a9` in a detached checkout, its original
exporters and an external reader harness (no candidate application code copied
into that checkout). Workout writes match exactly; preferences/playback exports
match after accounting for exporter-generated creation/update timestamps. All
12 released reader/serializer cases passed against the candidate. The existing
registered-client reader suite passed 108 tests including the two exporters.
These are source/contract tests, not an Android hardware reproduction.

unchanged. The separate source analyzer brace fix has no behavior change.

local source fixtures, not a running center class or production writes.

store review submission and hands-on 2.0.5/2.0.6 class testing are on hold.

Physical center-tablet reproduction and store approval remain separate from
automated verification. A successful diagnostic deployment is not proof that the
original intermittent connection fault is fixed.
