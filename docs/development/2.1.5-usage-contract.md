## 1. 확정 정책과 범위

모든 원장·API 값은 정수 **bytes**다. 사용자 표시 MB=1,000,000B, GB=1,000,000,000B, 시간 경계는 서버 KST(UTC+09:00) 일·월이다.

| policyPlan | 총보관 storageLimitBytes | 일 신규 uploadDayLimitBytes | 수업 imageLimitBytes | 일 downloadDayLimitBytes | 월 downloadMonthLimitBytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| free | 100000000 | 30000000 | 100000000 | 50000000 | 500000000 |
| premium | 1000000000 | 500000000 | 100000000 | 1000000000 | 20000000000 |

- 상품·선택지·혜택·오류 문구는 **Free / Premium**만 노출한다. Free 100MB/30MB, Premium 1GB/500MB 등 decimal로 표기한다. 기존 실제 스토어 가격·결제 종료·갱신·자동과금은 변경하지 않는다.
- Plus 판매 ID·선택지·일반 정책 분기는 제거한다. 과거 receipt, 권한 문서, 2.0.5 wire의 `plus` 해석은 격리한 legacy adapter에만 남긴다. 기존 grant를 Free/Premium으로 자동 치환하지 않는다. 기존 결제 관리/복원은 유지하며 UI는 `기존 구독 이용 중`으로 표시한다. 새 상품으로 자동 승격시키거나 새 quotaPlan을 추측하지 않는다.
- 수업·카운트다운·브랜드·프로필·사용자 생성 템플릿/AI 산출물의 소유 이미지 실물 파일을 합산한다. 배포 파일, 공통 center-templates 원본, 지원 첨부는 별도 서비스로 제외한다. 사용자 경로에 복제된 원본은 포함한다. 삭제되지 않은 orphan도 보관량이다.
- 동일 `(bucket,path,generation)` 재사용은 보관·신규 업로드 중복 차감하지 않는다. 다른 실물 파일 생성은 같은 내용이어도 새 업로드다. 삭제 후에도 당일 생성량은 환급하지 않는다. 삭제·압축·자동 정리·토큰 일괄 철회·캐시/중복 요청 최적화는 구현하지 않는다. 기존 최적화 동작을 확대하거나 정책 해결책으로 제시하지 않는다.
- 새 수업은 일/월 전송 여유와 cold 준비 예산을 모두 충족해야 한다. 진행 중인 동일 수업의 pause/resume/reconnect/복귀는 quota 초과·grant 만료 때문에 끊지 않는다. 초과 제공량은 `protectedOverageBytes`로 기록한다. 절대 전송/청구 상한이나 추가요금을 약속하지 않는다.

## 3. 공통 DTO / endpoint (서버·Dart 동일 필드명)

정의: `Bytes`/`Ms`=0 이상 JS safe integer / Dart int, `Id`=서버 검증된 비어 있지 않은 ID, GCS `generation`=decimal **string**, nullable 필드는 명시적으로 null이다. 응답에는 URL token·원시 예외를 넣지 않는다. callable는 `asia-northeast3`, schemaVersion=1, policyRevision=`image-usage-2.1.5-v1`이다. 아래 이름은 root export까지 그대로 사용한다.

```ts
type PolicyPlan = 'free' | 'premium';
type EnrollmentMode = 'legacy' | 'observe' | 'enrolled';
type Mutation = {schemaVersion: 1, requestId: string};
type AssetRef = {
  assetId: string, source: string, generation: string,
  sizeBytes: number, contentType: string, sha256: string
}; // source = 설정된 gateway의 안정된 HTTPS URL, lease/token 없음
type PeriodUsage = {
  key: string, resetsAtMs: number, limitBytes: number,
  grantedBytes: number, usedBytes: number, reservedBytes: number,
  unknownBytes: number, remainingBytes: number, protectedOverageBytes: number
};
type Usage = {
  schemaVersion: 1, policyRevision: string, mode: EnrollmentMode,
  policyPlan: PolicyPlan | null, measuredAtMs: number, revision: number,
  storage: {limitBytes: number | null, usedBytes: number,
    reservedBytes: number, unknownBytes: number, complete: boolean},
  uploadDay: PeriodUsage | null, downloadDay: PeriodUsage | null,
  downloadMonth: PeriodUsage | null,
  attribution: 'gateway' | 'partial_legacy' | 'unknown',
  nextEligibleAtMs: number | null
};
type UsageError = {
  schemaVersion: 1, policyRevision: string, reason: string,
  retryable: boolean, usage: Usage | null, requiredBytes: number | null,
  nextEligibleAtMs: number | null
}; // HttpsError.details / HTTP JSON {error: UsageError}
```

`usedBytes`는 gateway가 완료 응답 본문으로 제공한 양이며 cloud 청구/클라이언트 수신 ACK와 다르다. `unknownBytes`는 제공 가능성이 있지만 결과를 확정 못한 예약 상한으로, used/reserved와 **겹치지 않는** 버킷이다. remaining=`max(0,limit+유효grant-used-reserved-unknown)`. active protected 예약으로 음의 내부 잔액은 가능하지만 UI remaining은 0이다. legacy mode에서 unknown 전체량을 추정해 가짜 숫자로 채우지 않으며 `attribution`/`complete=false`로 측정 공백을 명시한다. `nextEligibleAtMs`는 두 기간·unknown·권한까지 판정 가능할 때만 값이 있고, 다음 자정에 무조건 가능하다고 표시하지 않는다.

`WorkoutWire`는 기존 saveWorkout의 workout JSON(소유자/author·타임스탬프 변환 포함)이며 별도 wire를 발명하지 않는다. 서버가 timing·소유자·자료 전체·권한을 검증하고 immutable snapshot을 만든다. 저장 안 한 초안도 검증된 전체 snapshot으로 시작할 수 있다. module imageUrl/countdownImageSource/브랜드 projection까지 manifest에 포함하고 클라이언트의 bytes/hash/TV 수를 신뢰하지 않는다. 요청은 기존 제한(900000B workout, 최대 이미지64/TV32 등)을 유지한다.

```ts
type Admission = {
  schemaVersion:1, admissionId:string, sessionId:string, epoch:number,
  manifestHash:string, clientFingerprint:string, policyRevision:string,
  status:'preparing'|'committing'|'active'|'cancelled'|'expired'|'completed',
  prepareExpiresAtMs:number, targetDeviceIds:string[],
  reservedDownloadBytes:number, usage:Usage
};
type StartIntent = {stepIndex:number,durationMs:number,briefing:boolean,
  scheduled:boolean,scheduledAtMs:number|null,updatedByDeviceId:string};
type UploadPermit = {
  schemaVersion:1, uploadId:string, expiresAtMs:number,
  status:'reserved'|'writing'|'stored'|'cancelled'|'expired'|'unknown',
  uploadUrl:string|null, asset:AssetRef|null
};
```

Idempotency: mutation key `(ownerId,endpoint,action,requestId)` + 서버 canonical payload hash. 같은 키/본문은 저장된 결과를 재조회하고 이중 예약하지 않는다. 같은 키/다른 본문은 `idempotency_conflict`다. requestId는 8..80 ASCII `[A-Za-z0-9_-]`, server IDs는 UUID를 사용한다. `prepare`가 만든 sessionId는 이후 commit/재시도/복귀에서도 그대로이며 현재 `prepare-*` 화면 요청 ID와 구분한다. `manifestHash`는 서버 canonical JSON(키 정렬, 순서 있는 modules, 정렬된 targets, asset generation·size, effective settings·브랜드 revision)의 SHA256이다. clientFingerprint는 로컬 내용 변경 탐지 전용이며 서버 인증 근거가 아니다.

실패 reason 고정: `daily_transfer_limit`, `monthly_transfer_limit`, `both_transfer_limits`, `insufficient_start_budget`, `storage_limit`, `daily_upload_limit`, `workout_image_limit`, `usage_reconciliation_pending`, `policy_or_client_upgrade_required`, `legacy_asset_transition_required`, `entitlement_unverified`, `idempotency_conflict`, `admission_expired`, `session_changed`, `media_lease_invalid`, `upload_mismatch`, `service_unavailable`, `grant_configuration_required`. quota는 resource-exhausted/HTTP429, 사전조건은 failed-precondition/409, 입력은 invalid-argument/400, 인증은 unauthenticated/401·permission-denied/403, 결과 미확정은 unavailable/503이다. 존재하지 않는 외부 계정·asset을 구분해 유출하지 않는다.

새 정책을 기존 subscriptionEntitlements/planUsage 문서에 덮어쓰지 않는다. 다음 문서는 client write 금지다.

| Firestore 경로 | 핵심 필드 / 목적 |
| --- | --- |
| `appConfig/imageUsage` | `schemaVersion,policyRevision,enabled,allowedProjectIds,grantLimits` (누락시 신규 enrollment/강제 적용 비활성) |
| `imageUsageAccounts/{uid}` | `mode,policyPlan,policyRevision,revision,consentRevision,eligibility,storageUsedBytes,storageReservedBytes,storageUnknownBytes,inventoryComplete,activeAdmissionId,nextEpoch` |

기간 key는 `YYYY-MM-DD`/`YYYY-MM`, document ID는 예: `downloadDay_2026-11-14`. 요청 수락 시각의 일·월에 응답 전체를 귀속한다(자정 걸친 한 body를 임의 분할하지 않음). 다음 요청은 새 기간에 귀속한다. 준비 예산을 옛 기간에 예약했어도 body 직전 새 기간으로 **원자적으로 재배정**한다. 준비 중 여유 부족이면 거절, active이면 protected overage로 재배정한다. grant도 정확한 기간 키에만 배정한다.

`functions/src/image-usage-ledger.js`는 다음 이름을 export한다. 모든 ctx는 `{db,realtime,auth,bucket,projectId,clock}` 중 필요한 의존성을 받고 함수는 Promise를 반환한다. timestamp는 clock(기본 Date.now), tx 내부 네트워크 body 요청은 금지다.

```ts
readUsage(ctx,{ownerId}): Usage
requireUsageContext(ctx,{actorUid,ownerId?,purpose,sessionId?,admissionId?}):
  {ownerId,actorUid,deviceId:string|null,mode,policyPlan,protected:boolean}
reserveUpload(ctx,{ownerId,requestId,payloadHash,purpose,workoutId,sha256,sizeBytes,contentType,path}): UploadRecord
beginUpload(ctx,{ownerId,uploadId,actorUid}): UploadRecord
settleUpload(ctx,{ownerId,uploadId,outcome:'stored'|'not_written'|'unknown',asset:AssetRecord|null}): UploadRecord
reserveTransfer(ctx,{ownerId,actorUid,deviceId,leaseId,assetId,generation,sizeBytes,admissionId,sessionId,purpose}):
  {attemptId,reservationId,protected:boolean}
settleTransfer(ctx,{ownerId,attemptId,outcome:'served'|'not_sent'|'unknown',bodyBytes:number}): void
```

`UploadRecord`=UploadPermit + 비공개 ownerId/path/sha256/sizeBytes/contentType/purpose/workoutId/reservationId, `AssetRecord`=AssetRef + bucket/path/ownerId/tokenFree/provenance. B는 계정/period/grant 카운터를 직접 쓰지 않고 A의 settleUpload로 자산 등록을 확정한다. A는 HTTP body 해석/GCS 객체 생성을 맡지 않는다. 서로의 모듈 인터페이스는 변경하지 않는다.

모든 변경은 계정 직렬화 doc과 관련 기간·예약·멱등 결과·감사를 **동일 Firestore transaction**에서 읽고 쓴다. Firestore+Storage 또는 Firestore+RTDB는 단일 transaction이 아니다. 완료 확정이 없으면 timeout만으로 예약을 환급하지 않는다. used/reserved/unknown 사이 이동은 attempt별 단 한 번이며 중복/역순 settle이 이미 served를 unknown/0으로 되돌릴 수 없다.

신규 upload: 실제 size를 서버로 확인할 수 없는 reserve 단계에서는 선언 size를 상한으로 예약한다. body size/hash/type/이미지 signature 확인 후 동일 permit만 저장한다. beginUpload의 reserved→writing claim은 한 writer만 획득하며 writing 중 cancel/TTL은 환급하지 않는다. 쓰기 결과가 불명확하면 generation metadata 대사 전까지 storage+upload 예약을 unknown으로 보존한다. `not_written`은 늦은 writer fence와 실제 미생성을 입증할 때만 환급한다. stored는 보관량과 일 생성량으로 이동하며 고유 경로의 ifGenerationMatch=0으로 재시도를 멱등 처리한다. object overwrite는 허용하지 않는다. 기존 파일 삭제로 줄어드는 보관량은 generation별 실제 삭제를 입증할 때 한 번만 반영하되, 이번에는 자동 삭제 작업을 추가하지 않는다. 만료 준비 예약도 이미 배정된 HTTP attempt는 보존하고 미배정 잔여분만 취소한다.

보관량은 inventoryComplete가 검증된 계정만 강제 적용한다. 새 계정의 빈 namespace는 검증된 0으로 시작할 수 있다. 과거 inventory를 API 조회 없이 0으로 초기화하지 않는다. 신규 server-generated 사용자 이미지도 동일 reserve→store→settle을 거치며 크기 미상은 최대 허용 출력 크기를 먼저 예약하고 실제 size로 정산한다. 기존 서버 이미지 제공 callable은 enrolled에서 gateway descriptor로 전환하거나 같은 원장을 통해 실제 응답 body bytes를 정산한다.

## 5. 준비·start·복귀와 cross-store fence

1. enrolled 컨트롤러는 이미지 prefetch/TV 준비 게시 **전** prepare를 호출한다. owner의 Firebase ID token(폐기 검증 포함), entitlement, TV displayAccess/device/revocation/authAccess/deletion lock, 소유 이미지 메타데이터·generation·capabilities를 서버가 확인한다. 비어 있는 targets는 서버에서 현재 검증된 목록으로 확정해 반환한다. cold 예산=`각 허용 participant가 받을 고유 원격 이미지 size 합계`이며 선택 TV와 컨트롤러 1대를 포함한다. 로컬 렌더/번들 리소스는 전송량 0이며 원격 fallback은 포함한다. 캐시 보고로 예산을 줄이지 않는다.
2. FS transaction으로 일/월 예산·활성 slot·epoch를 함께 예약하고 preparing+outbox를 쓴다. preparing TTL은 **90000ms**(기존 준비 시간 유지). 이미 preparing/active가 있으면 같은 멱등 요청을 복구하거나 session_changed다. 예약 불가면 RTDB request도 body도 발생하지 않는다.
3. outbox가 RTDB `users/{uid}`에서 transaction으로 server-only `usageGate`와 schema2 preparation request를 함께 게시한다. request는 기존 images/sounds/targets 형식 + admissionId/sessionId/epoch/manifestHash를 갖는다. TV는 새 capability `imageUsageProtocol:1` 및 `preparationProtocol:2`를 광고한다. 구 schema1 협상은 legacy/observe에서 유지한다. enrolled는 모든 대상이 신 경로를 지원해야 한다.
4. TV/컨트롤러는 ID token으로 lease를 발급받고 허용 자산만 gateway로 요청한다. prepare 예약을 participant/asset attempt에 배정한다. HTTP 재요청은 매번 별도 attempt이며 준비 예산을 넘으면 추가 여유를 확인한다. 기존 cache/dedup 동작은 그대로 사용하되 새 최적화는 추가하지 않는다. 예측 cold량을 used로 청구하지 않는다.
5. commit은 같은 admission/manifest/epoch/targets와 유효 준비 영수증, 최신 entitlement·grant·prepared snapshot을 검사한다. FS가 committing/outbox를 확정한 후 RTDB transaction으로 같은 epoch의 immutable snapshot·activeSession·usageGate를 함께 게시한다. 현재 미완료 세션을 교체하지 않으며 오래된 epoch outbox는 abort한다. startAt/anchor/notificationCommand 만료는 서버 시각으로 만든다. start 입력의 duration/step은 서버가 workout timing과 대조한다.
6. **RTDB 게시 후 FS finalize 실패는 시작 실패로 환급하지 않는다.** RTDB의 같은 epoch/session을 durable evidence로 취급해 committing도 보호하고, get/같은 commit 재시도/재시도 outbox가 FS active를 수렴시킨다. 클라이언트는 committing을 `시작 상태 확인 중`으로 표시하고 새 sessionId로 다시 시작하지 않는다. 서버가 RTDB에 게시 안 됨을 입증한 경우만 취소·예약 환급한다. 응답 성공은 실제 RTDB 게시를 확인한 뒤에만 반환한다.
7. active는 준비/lease TTL로 완료되지 않는다. 같은 sessionId+epoch+manifest+기존 participant의 pause/resume/seek/briefing begin/복귀는 새 admission을 요청하지 않는다. 짧은 media lease(300000ms)가 만료되면 기존 active binding으로 갱신하며 quota 때문에 막지 않는다. replacement TV·새 targets·다른 명세는 이번에 허용하지 않는다. 기존 미완료 수업의 기간 무제한 보호와 적대적 반복 수신의 절대 상한을 동시에 보장할 수 없다.
8. 완료/명시 종료는 RTDB의 기존 completion 기록을 확인해 FS terminal outbox로 수렴시킨다. A는 해당 onValueWritten handler와 get 시 대사를 제공한다. timeout/TV offline만으로 completed를 만들지 않는다. completed 후 재시작은 새 admission이다. 자연 진행 완료는 기존 completion evidence를 사용하고 서버가 단순 duration+벽시계만으로 진행 수업을 끊지 않는다.

RTDB `usageGate`={mode,policyRevision,enrollmentRevision,epoch,admissionId,sessionId,manifestHash,phase,preparedSnapshotId}. enrollment revision이 준비·start·규칙에 일치해야 한다. RTDB read-then-write를 검증이라고 부르지 말고 실제 transaction 안에서 epoch/기존 active를 검사한다. FS가 active/committing인 동안 다음 epoch 발급을 차단하며 outbox 재실행은 기존 active 내용을 덮어쓰지 않는다. enrolled에서 직접 activeSession 생성/교체, snapshot 생성, preparation request 쓰기는 막는다. 기존 control transaction은 동일 identity·immutable workout/snapshot/targets/binding을 보존하는 한 허용한다. 전체 activeSession 삭제로 fence를 우회하지 못하게 한다.

전환 시 이미 존재하는 legacy active는 서버가 identity/snapshot/targets를 보존한 grandfather binding을 만든 뒤 동일 수업 복귀만 보호한다. 검증된 binding 없이 enrolled로 전환하지 않는다. quota 관련 플래그로 auth revocation/소유권 검사를 우회하지는 않는다.

## 6. 실제 media body와 upload 전달 (B)

- **선정:** 2세대 onRequest의 작은 이미지 **buffered response**, GCS metadata 확인→원장 예약→generation 고정 download→`response.end(buffer)`. 기존 `<10485760B` 이미지 허용, profile `<5242880B`를 유지한다(한도 제품 표시는 위 decimal 정책과 별개). 10MiB 근처 파일은 streaming 10MB 경계를 넘을 수 있으므로 pipe/flushHeaders/chunked streaming은 사용하지 않는다. 32MB non-streaming 범위 안에서 byte 원본을 그대로 전송한다. 함수 초기 권장 memory=512MiB, concurrency=4, timeout=60s이며 root가 source export에 반영한다. 여러 이미지를 한 응답으로 묶지 않는다.
- `cloudboardMedia`: GET만 image body 200 제공. source query는 `assetId`/`v`만, `Authorization: Bearer <Firebase ID token>` + `X-CloudBoard-Media-Lease: <leaseId>` 필수. lease는 actor UID/device binding·owner·asset generation·purpose·session/manifest/epoch에 묶은 server record이며 URL 서명으로 대체하지 않는다. ID token을 URL/RTDB/log에 넣지 않는다. raw signed GCS URL/302 redirect는 반환하지 않는다.
- HEAD는 같은 auth/lease 검증 후 metadata만 200, body 0, lease 소비 없음. OPTIONS는 CORS만 처리. Range는 416, conditional 304는 이번 미지원(조건부 header는 무시하고 유효 GET은 200 body 전체). `Cache-Control: private,no-store`, 고정 Content-Length/Content-Type, `X-Content-Type-Options:nosniff`, ETag는 generation으로 고정하되 재검증 최적화는 추가하지 않는다. Content-Encoding 변환·압축은 하지 않는다.
- body 다운로드 전에 `reserveTransfer`를 성공시킨다. active session 요청은 capacity 거절 없이 protected 예약을 만들지만 인증/manifest/asset 검증은 동일하다. getMetadata 자체의 서비스 비용과 이미 서버로 들어온 invalid request 비용까지 사라진다고 주장하지 않는다.
- Node `finish`는 buffer 본문이 플랫폼으로 전달됐다는 서버 관측이며 클라이언트 완전 수신 증거가 아니다. finish면 served bodyBytes=buffer.length, 확실한 body 미전송이면 not_sent/0, close/error/프로세스 crash로 전달량 불명이면 unknown(size 상한). finish 전에 성공 정산하지 않는다. finish 뒤 정산 crash도 durable attempt가 남아 unknown으로 대사한다. 플랫폼이 client 취소 후에도 body를 전송할 수 있으므로 unknown을 0 환급하지 않는다. 같은 lease 재요청은 새 attempt로 다시 제공량을 센다. HTTP header/TLS/Storage 내부 fetch/청구 전송량은 별도 측정점이다.
- `cloudboardImageUploadBody`: POST raw bytes, ID token + `X-CloudBoard-Upload-Id`, permit 정확 size/hash/type, 서버 인가 확인 후 private `users/{uid}/managed-images/{purpose}/{uploadId}/{sha256}`에 Admin SDK create-only 저장. SDK public token을 생성하지 않는다. body 201 `{schemaVersion:1,upload:UploadPermit}`, 재시도 stored는 동일 asset 결과. HTTP 중단/결과 모호함은 upload get으로 조회하고 새 uploadId로 중복 저장하지 않는다. raw input은 32MB보다 충분히 작지만 reserve 거절 전에 보낸 악성 ingress 자체를 통제하는 정책은 아니다.
- managed asset.source는 `https://asia-northeast3-<명시project>.cloudfunctions.net/cloudboardMedia?assetId=<id>&v=<generation>`이고 업로드 결과에도 TTL lease를 저장하지 않는다. 서버 메타데이터 checker·designFingerprint/reuse 코드는 새 source도 자산 registry로 해석한다. canonical gateway hostname/project/asset 소유를 검증하며 arbitrary URL fetch/SSRF는 금지한다.
- 과거 Firebase token URL/gs URL은 허용된 버킷/owner 경로의 메타데이터만 해석한다. 외부 provider URL은 임의 proxy하지 않는다. legacy/observe의 기존 provider/HTML fallback은 보존한다. enrolled 새 수업에 tokenFree registry로 검증되지 않는 원격 자산이 포함되면 `legacy_asset_transition_required`로 **전송 전** 거절한다. 옛 URL을 지우거나 기존 파일을 자동 복제하지 않는다.
- AI raster/template job 원격 결과도 같은 등록·reserve 경로를 호출한다. raw 이미지/base64를 기존 callable로 제공하는 enrolled 분기는 계측 descriptor로 바꾸거나 그 callable 실제 body를 동일 ledger로 센다. 해당 경로를 제외하고 전체 사용자 이미지 quota 완료라고 보고하지 않는다. 기존 job의 lease/재시도/출력 호환을 보존한다.

공식 제한 확인(2026-11-14): [Cloud Run functions quotas](https://docs.cloud.google.com/functions/quotas)는 2세대 streaming 10MB/non-streaming 32MB를 구분한다. [Flutter Image.network](https://api.flutter.dev/flutter/widgets/Image/Image.network.html)는 HTML image 경로에 headers 제약이 있다. 따라서 web도 managed 이미지에는 기존 http 패키지로 bytes를 받아 MemoryImage로 표시한다. 이 선택은 본문을 대리 제공하는 설계이며 실제 플랫폼 완주 증거는 후속 검증으로 남긴다.

## 7. Flutter·rules·상품 통합 (C)

`View → Controller → UseCase → Repository → DataSource`와 기존 Riverpod 계정 수명을 유지한다. 새 feature `image_usage/{domain,data,presentation}`에 위 DTO/실패/조회·admission·media/upload source를 두고 외부 에러를 Failure로 매핑한다. 생성 코드·provider 등록이 필요한 입력만 바꾸고 root가 build_runner를 한 번 실행한다.

- prepare/start pending·결과 미확정·거절을 구분한다. Usage는 앱 성공을 추정하는 로컬 카운터가 아니며 서버 값을 읽는다. 계정/TV owner 변경 시 이전 요청 결과/lease가 새 scope에 적용되지 않게 epoch/dispose 검사한다.
- controller prepare → server Admission → server-published preparation watch → TV receipt → commit 순서로 연결한다. 기존 `preparationFingerprint`와 서버 manifestHash를 혼동하지 않고 로컬 clientFingerprint와 서버 binding을 각각 보관한다. bypass 가능한 기존 직접 RTDB fallback은 enrolled 오류 경로에 두지 않는다. legacy/observe는 기존 동작을 명시 분기한다.
- 새 managed source는 UI·precache·retention·color sampling·디자인 재사용·브랜드·avatar·template 표시까지 공통 media source로 해석한다. async ID token/lease 발급 뒤 `http` bytes fetch를 사용한다. web에 Authorization header를 못 붙이는 HTML fallback으로 넘기지 않는다. 기존 단순 `ImageProvider(source)` 동기 경로만 바꿔 준비 이미지는 옛 token으로 받게 남겨두면 미완료다.
- gateway CORS는 source에 명시한 허용 web origins + 로컬 emulator origin만 허용한다. GET/HEAD/OPTIONS와 upload POST, `Authorization`, `X-CloudBoard-Media-Lease`, `X-CloudBoard-Upload-Id`, `Content-Type` preflight 및 필요한 response header 노출을 지원한다. credentials cookie는 사용하지 않는다. Firebase Hosting의 현재 catch-all HTML rewrite에 gateway를 맡기지 않으며 function URL을 직접 사용한다. 실제 origin 미확정이면 origin을 추측해 전체 허용하지 않고 fixture/local만 검증한다.
- quota 거절은 한 번만 사용자에게 안내하고 로컬 초안·기존 자료를 유지한다. 예: `이미지 전송 한도에 도달해 새 수업을 시작할 수 없어요. 진행 중인 수업은 계속할 수 있어요.` 일/월 한도·사용/예약/미확정·기준 시각을 구분하고 서버 조회 실패는 `사용량 확인 실패`다. 진행 수업으로 돌아가기·재연결을 열어 둔다. 관리자 즉시 승인/24시간 대응은 약속하지 않는다.
- storage rules: managed namespace는 모든 client get/list/create/update/delete 금지(Admin gateway만). enrolled 계정의 옛 image namespace 직접 SDK get/create/update를 막고 기존 명시 삭제 권한은 원래 범위에서 유지한다. token URL은 Rules만으로 철회되지 않으므로 eligibility에 tokenFree 조건이 필수다. observe/legacy는 원 규칙 유지한다. 지원 첨부/center-template 권한을 넓히지 않는다.
- Firestore: usage 원장 private, `cloudboardImageUsage`로만 요약 제공. enrollment·grant·asset·attempt client write 금지. RTDB usageGate는 server only; ancestor `.write`가 child 차단을 무효화하지 않는지 확인한다. devices의 새 capability만 제한적으로 허용하고 권한·session binding은 client 수정 불가다.
- C가 `plan-policy.js`/billing catalog의 공개 상품 enum을 free/premium으로 좁히고 `legacy-plan-adapter.js`에 과거 Plus capability/receipt product mapping을 격리한다. billing/google-play 검증·renewal/restore는 이 adapter를 사용한다. 이전 grant의 expiry/개별 capability·source·revision을 보존하며 old reader 필드/endpoint를 삭제하지 않는다. 신규 판매 목록과 구매 호출은 Premium만 허용한다(Free는 구매 아님). store readiness는 실제 Premium 증거만 검증하고 없는 증거를 만들지 않는다. 새 UI에서 Plus/플러스 혜택·CTA·오류문구가 남지 않게 한다.

## 8. enable·전환 및 관리자 증액

- source의 기본은 **disabled**, config 누락이면 신규 enrollment를 만들지 않는다. 이미 enrolled인 계정을 config 누락/비활성만으로 legacy 직접 경로로 되돌리지 않으며, 새 입장은 확인 불가로 보류하고 기존 active는 보호한다. 허용 개발 프로젝트는 `cloud-board-development`, 로컬 `demo-*`만. 운영 `cloud-board-stationd`의 신규 enforcement/enrollment는 이번 코드 경로에서 거절한다. 환경값 누락을 개발로 추정하지 않는다. 이 작업은 어느 Firebase에도 config를 쓰거나 배포하지 않는다.
- legacy: 이전 결제·권한/RTDB·URL 보존, 사용량 귀속 unknown. observe: 새 gateway 경로를 계측할 수 있지만 direct legacy 공백을 partial_legacy로 표시하고 quota 차단을 켜지 않는다. enrolled: 명시 정책동의·검증된 free/premium mapping·inventoryComplete·모든 이미지 tokenFree·server-only admission/rules projection·모든 대상 capability가 충족된 **개별 계정**만 강제한다. 새 계정도 조건을 자동 생략하지 않는다.
- enrollment는 A의 서버 내부 `setUsageEnrollment(ctx,{ownerId,mode,policyPlan,consentRevision,requestId})`로만 수행한다(공개 callable 없음, 로컬 fixture용 호출만 이번 검증에 허용). 준비중인 활성화를 ready로 표기하지 않고 enrollmentRevision을 FS에 기록→RTDB fence 게시/검증→FS enrolled 확정한다. pending 불일치 중 새 준비는 막되 기존 binding 복귀는 유지한다. legacy→observe는 비파괴, enrolled→observe rollback도 감사 revision으로 남기며 ledger/lease/active를 삭제하지 않는다. rollback이 gateway 장애를 자동 해결하지는 않는다.
- 과거 token URL이 살아 있고 2.0.5 직접 start/upload를 허용하는 미전환 계정에 전체 실제 전송 강제는 불가능하다. 전체 토큰 철회·기존 앱 차단 없이 이를 해결했다고 보고할 수 없다. 기존 계정 전환·Plus 권리 결정·실물 혼합 클라이언트 검증은 운영 적용 선행조건이며 이번에 실행하지 않는다.
- grant는 서버 `quotaOperator === true` custom claim, revoked token 검증, auth_time 최근 5분을 검사한다. 계정 소유자/익명 TV는 발급·조회 불가. additionalDayBytes/additionalMonthBytes는 각각 0 이상이고 하나 이상 양수, exact day/month key, 명시 유효기간·필수 사유(10..1000자), operator UID/requestId/payloadHash/전후 revision/audit를 같은 FS transaction에 쓴다.
- `appConfig/imageUsage.grantLimits={maxAdditionalDayBytes,maxAdditionalMonthBytes,maxValidityMs}`가 없거나 유효하지 않으면 `grant_configuration_required`로 거절한다. 운영 권한/한도 설정이 존재한다고 가정하지 않는다. emulator fixture에만 유한 값을 둔다. grant 유효기간은 target KST일 안에, targetMonthKey는 그 날의 월로 제한한다. 여러 날 지원은 별도 grant로 명시한다.
- 기본 예산 먼저, 그 뒤 만료 빠른 grant 순으로 reservation allocation을 고정한다. 양기간을 따로 검사하고, 중복 grant는 한 번만 적용한다. 취소/만료의 미사용분만 제거하며 이미 active인 수업을 끊지 않는다. preparing은 commit 때 유효 grant로 재검사한다. grant expiry가 이미 소비된 사용량을 0으로 만들지 않는다. 자동 결제/무제한 bypass flag는 없다.

## 9. 병렬 담당 파일·직렬 통합

3명 이내, 추가 워커 재위임 없이 root가 배정한다. 모든 `*.g.dart`, `*.freezed.dart`, lockfile, `functions/src/index.js`, pubspec, 공통 설정·배포 파일, Git/PR은 **root 단독**이다. 아래 외 경로 수정 필요 시 root에게 먼저 소유권을 넘겨받는다. 테스트 파일 소유도 함께 분리한다.

root 직렬 순서: (1) A/B/C가 이 계약으로 병렬 구현·각자 관련 단위 검증, (2) A 실원장 결과와 B gateway를 연결, (3) root index exports/onCall revoked auth wrapper/onRequest CORS/FS trigger·RTDB outbox trigger 연결, (4) C wiring와 generated code 일괄 생성 및 source/설정 해석 통합, (5) 필요한 로컬 emulator 계약·앱→callable→저장→재조회 검증, (6) 2.1.5 버전·증거 문서·develop PR. emulator용 project/config fixture는 실제 운영 설정과 분리한다. 이번 태스크와 후속 source 작업 모두 실제 개발 Firebase 배포·운영 변경·태그·main 승격은 포함하지 않는다.

root index가 연결할 export: `cloudboardImageUsage`, `cloudboardClassAdmission`, `cloudboardMediaLease`, `cloudboardMedia`, `cloudboardImageUpload`, `cloudboardImageUploadBody`, `cloudboardUsageGrant`; FS outbox retry handler, RTDB completion 대사 handler, server-generated image accounting 주입. public callable handler는 `handleImageUsage`/`handleClassAdmission`/`handleMediaLease`/`handleImageUpload`/`handleUsageGrant`이며 모두 `{...ctx,actor,input}`를 받는다(actor는 root가 폐기 검증한 `{uid,token}`). ## 10. 최소 회귀 검증과 남는 공백

이번 문서 작성에서 구현/테스트/빌드 명령은 **미실행**. 문서·JSON 형식/정책값 확인만 수행한다. 후속 담당은 필요한 아래 범위만 실행하고 관련 통과 후 전체 CI/전 플랫폼 빌드로 확대하지 않는다.

- A: Free/Premium 정확 bytes 및 KST 자정/월말, 마지막 잔여량 동시 prepare/upload, 같은 키 재시도/본문 변조, expiry/revoke/grant 경합, 준비 취소·unknown 무환급, RTDB 게시 전후 crash·epoch 역순·ACK 유실, quota 초과 active pause/resume/reconnect/completed 후 새 시작 거절.
- B: metadata→예약 전에 body fetch 없음, 원본 10000000B 초과~10485759B buffered 실제 HTTP body 전달, hash/size 위조·동시 upload·lost response·generation 정산, HTTP GET/HEAD/OPTIONS/Range·취소/finish/crash·중복 settle, lease 다른 UID/TV/owner/session 재사용 거절, 기존 token/provider 미상, AI 출력/다운로드 우회 없음.
- C: enrolled 직접 RTDB start/preparation/snapshot 및 managed Storage 우회 거절, legacy/observe 구 계약 허용과 grandfather controls, auth/deletion/revocation·anonymous TV pairing regression, Premium만 신규 구매 표시와 legacy receipt restore, UI decimal·일/월 거절·조회 실패·진행수업 복귀·초안 보존, web http CORS 경로와 native provider 분기.
- root 통합: 로컬 Firebase Auth+Firestore+RTDB+Storage+Functions emulator에서 **실제 callable 구현**을 거친 reserve→raw upload→registry 재조회→prepare→gateway body→commit→한도 후 동일 세션 복귀. 관련 기존 `workout-image-budget`, `plan-policy`, `billing-policy`/Play 및 playback start/preparation/continuity 테스트를 영향 범위에서 재사용한다. mock만이면 앱 저장 성공/전체 E2E 통과라고 부르지 않는다.
- 앱 저장 변경의 필수 증거는 앱 빌드·정확 source SHA·emulator project/포트·서버 revision·실제 저장 후 재조회 결과다. Firebase 계정/외부 설정 부재로 연결 못 하면 **미확인**으로 남긴다. 개발 Firebase 연결은 이번 미실행, 운영/스토어/실물 TV·2.0.5 혼합·실제 Functions 32MB buffering·cloud 청구 대사는 미확인이다. local HTTP는 로컬 통합 증거이지 managed runtime 전달 상한의 배포 증거가 아니다.

release support ledger/과거 fixture는 유지한다. `docs/released-client-compatibility.md` 기준의 실제 installed-client 전체 통합 검증은 root가 출시 단계에서 다루며 이번 기능 PR을 위해 무거운 전체 계약을 관성적으로 반복하지 않는다. STA-184 앱 E2E는 구현·실행 증거 없이 통과로 기록하지 않는다.

## 11. 구현 중 확정된 계약 보완

최초 설계와 다음 차이를 적용했다. 최종 근거는 구현 기록과 실제 소스다.

- 전환은 RTDB `mode=enrolling`의 requestId/hash/revision claim을 먼저 원자적으로 확보하고 Firestore를 갱신한다. 원래 요청·자동 복구의 중복 실행은 이미 시작된 수업과 더 최신 claim을 보존한다. `reconcileUsageEnrollment`와 `retryImageUsageEnrollment`가 복구한다. 이미 활성 legacy 수업은 전환하지 않는다.
- controller-only 수업을 유지한다. 선택 TV가 없고 연결 TV도 없어도 컨트롤러 1대 예산으로 준비할 수 있다.
- 기존 지원 형식인 data URI/bare base64 PNG/JPEG/WebP/GIF는 엄격히 검증해 `manifest.localAssets`로 고정한다. 로컬 자료는 이미지 100MB 합계에는 포함하고 Storage 전송 예약에서는 제외한다. 준비 요청/영수증 imageCount는 local+remote 전체다.
- admission은 `targetBindings`로 displayUid/pairingCode/pairedAtMs를 고정한다. 같은 deviceId에 다른 TV가 페어링돼도 기존 수업의 재연결 권한을 넘기지 않는다.
- uploadId와 canonical 경로는 원장에서 발급한다. 서버 생성 파일은 SHA가 확정되기 전 `sha256:null`과 유한 상한으로 예약하고, writer claim 후 `bindGeneratedUpload`로 실제 출력 SHA/크기/경로를 고정한다. 공개 raw upload는 이 모드를 요청할 수 없다.
- paired TV의 수업 없는 preview는 현재 서버 brand의 등록된 로고/배경/프로모션 자산만 허용한다. lease와 매 body에서 현재 소유·페어링·철회·허용 자산을 재확인하고 일반 전송 한도를 적용한다.
- enrolled/enrolling 브랜드 저장·projection은 등록 소유 자산과 generation 고정 token-free metadata를 확인한 뒤 users transaction에서 상태·검증 source를 재확인한다. 기존 계획 버전1 Admin 분기로 우회할 수 없다. 거절 시 이전 브랜드/수업을 유지한다.
- enrolled/enrolling의 직접 brand/수업/준비/snapshot 쓰기를 막고, 프로필·카운트다운의 새 원격 이미지 포인터도 검증한다. 기존 값 유지·명시적 clear와 지원 로컬 이미지 형식·legacy/observe·기존 삭제 계약을 보존한다.
- 공개 HTTP/Callable 이름은 원 계약을 유지한다. 신규 7개 API와 outbox/enrollment retry/completion reconciliation 3개 trigger는 개발/demo에만 source 노출하며 운영은 omit한다. 개발 source 배포 목록에는 추가했지만 태그/배포는 실행하지 않는다.
- demo Functions emulator는 명시적 로컬 mediaBaseUrl과 debug client bootstrap으로만 HTTP 전달을 허용한다. 운영/개발 실서비스 origin 자동 허용은 없다.
