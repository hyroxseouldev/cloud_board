## 호환성 및 범위

- Firebase 서버 데이터 구조와 보안 규칙은 변경하지 않았다. 기존 앱과 동일한 `activeSession` 구조로 통신한다. 따라서 서버 트랜잭션 자체의 전체 스냅샷 범위는 유지된다.
- 로컬 `xonboard.active-playback.v1` 데이터는 최초 읽기 때 v2로 이전한다. 새 스냅샷을 저장한 뒤 체크포인트를 교체하고, 그 작업이 성공한 후 이전 스냅샷을 정리한다. 이는 SharedPreferences API의 쓰기 완료를 기준으로 하며 데이터베이스 수준의 트랜잭션 보장을 추가한 것은 아니다.
- 인증/매장 소유자 판별이 아직 진행 중이면 로컬 재생 정보를 노출하거나 삭제하지 않는다. 소유자가 확정된 후 일치 여부를 검사한다.
- 수업 시작 전 전체 이미지 확인은 유지한다. 병렬 준비를 사용하며 실제 재생의 메모리 캐시는 작은 범위만 앞서 준비한다. 각 기기의 메모리 캐시는 OS 및 Flutter의 정책에 따라 퇴출될 수 있다.
- 운동 상세 문서의 서버 스키마는 유지한다. 검색·폴더·예약을 위해 전체 목록은 결국 읽으며, 이번 변경은 캐시 우선 표시와 단계적 수신을 적용한다. 별도 요약 컬렉션이나 서버 검색 인덱스는 추가하지 않았다.

## 실기기 비교 방법

동일 기기·네트워크·수업 자료로 변경 전후를 비교한다. 최초 실행과 캐시가 있는 재실행을 구분하고, 이미지가 많은 수업과 긴 수업을 포함한다.

1. 시작 시간: 프로세스 시작 → 첫 화면 → 목록/TV 대기 화면 사용 가능까지 각각 기록한다.
2. 수업 준비: 이미지 캐시 없음/있음 각각에서 준비 버튼을 누른 시점부터 시작 가능까지 기록한다.
3. 재생: `flutter run --profile -d <device-id>` 및 DevTools로 빌드/래스터 프레임, 메모리 최고치, GC를 확인한다. 60Hz 기기는 UI 및 raster 작업 각각의 16.7ms 초과 프레임을 비교한다.
4. 동기화: 브리핑 → 시작 → 일시정지 → 재개 → 같은 슬라이드 재시작 → 다음 슬라이드 → 종료, Wi-Fi 단절/재연결과 앱 재실행을 확인한다.
5. 목록: 24개를 넘는 운동과 여러 폴더를 준비하고, 페이지 수신 중 검색/저장/삭제 및 예약을 확인한다.
