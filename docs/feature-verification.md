# 기능 검증과 배포 인계

기능 개발 담당자가 변경한 기능을 검증하고 결과를 인계한다. PR과 `develop`에서는 코드와 그 증거를 검토하며, 출시 후보의 무거운 통합 검증은 `main` 배포 직전 한 번 수행한다. 서버·웹 배포와 모바일 업로드는 별도로 실행한다.

이 문서는 STA-181의 작업·검증 정책이다. 문서를 작성하거나 PR을 제출한 사실만으로 GitHub 자동 실행이 변경되지는 않는다. 워크플로 변경이 대상 브랜치에 반영되고 트리거·배포 의존 조건이 확인되어야 해당 자동화가 적용된 것이다. 저장소의 필수 검사 설정과도 일치하는지 확인해야 한다.

## 단계별 책임

| 단계 | 담당과 확인 내용 | 다음 단계로 전달할 것 |
| --- | --- | --- |
| 기능 개발 | 개발 담당자가 변경한 정상 흐름·실패 처리·기존 호환성을 관련 범위에서 검증 | 코드, 검증 대상 커밋, 실행 명령·결과·증거, 한계 |
| PR / develop | 리뷰어와 통합 담당자가 코드 및 기능 검증 증거를 검토 | 해결된 리뷰, 필요한 경우 영향 범위 재검증, 통합 후보 |
| main 배포 전 | 통합 담당 흐름이 실제 배포 대상 커밋에 대해 필수 통합 검증 수행 | 성공한 동일 커밋의 검증 결과와 배포 산출물 |
| 서버·웹 배포 | 검증 성공을 확인하고 해당 서버·웹 변경 배포 | 배포 커밋·환경·결과 |
| 모바일 배포 | 모바일 변경을 배포할 필요가 있을 때 별도 수동 실행 | 검증된 커밋, 서버 호환성, 빌드·업로드 결과 |

PR과 `develop`에서 무거운 전체 테스트·계약 검사·모바일 빌드를 자동으로 반복하지 않는 것이 목표다. 필요한 가벼운 형식 검사나 증거 확인은 기능 검증을 대체하지 않는다. 개발 환경을 갱신했다는 사실도 통합 검증이나 운영 배포 성공의 증거가 아니다.

## 기능 개발 단계의 완료 기준

변경한 기능에 대해 다음 세 가지를 확인한다. 관련 없는 경우에는 그 이유를 적는다.

1. **정상 흐름:** 사용자가 해당 동작을 시작하여 기대하는 결과까지 도달한다. 값이 저장되는 기능은 다시 읽었을 때 결과가 유지되는지 포함한다.
2. **실패 처리:** 이번 변경과 관련된 입력 오류, 권한 거부, 네트워크 실패, 재시도·취소 등에서 잘못된 성공 안내나 데이터 손상이 발생하지 않는다. 모든 기능에 모든 장애 조합을 강요하지 않는다.
3. **기존 호환성:** 변경의 영향을 받는 기존 화면·데이터·클라이언트 동작이 유지된다. 서버·규칙·직렬화 변경은 현재 배포된 앱·TV 및 기존 웹 탭이 사용하는 계약을 확인한다.

검증 범위는 실제 위험과 변경에 비례한다.

| 변경 유형 | 기능 단계에서 필요한 확인 예 | 이것만으로 주장할 수 없는 것 |
| --- | --- | --- |
| 문구·문서 | 변경 내용, 링크, 의도하지 않은 수정 확인 | 앱 전체 회귀 검증 |
| 단순 시각 변경 | 관련 화면의 배치·잘림·상태 확인, 영향을 받는 크기나 플랫폼 확인 | 모든 기기의 완전한 동일성 |
| 상태·계산·검증 로직 | 변경한 분기와 경계값의 관련 유닛 테스트 | 실제 SDK·네트워크 성공 |
| 화면 상호작용 | 관련 위젯 테스트 또는 실제 앱 조작, 실패 상태·기존 흐름 확인 | mock 너머의 서버 저장 성공 |
| 앱 저장·동기화 | 관련 로직 검사와 실제 앱→실제 callable→저장→재조회 확인 | 실제로 사용하지 않은 환경의 성공 |
| 서버·접근 규칙·계약 | 영향받는 허용·거부·기존 클라이언트 계약의 집중 검사 | 모든 설치 버전·실기기의 동작 |
| 워크플로·도구 | 변경한 설정의 빠른 유효성 검사와 조건·실패 경로 확인 | 아직 실행하지 않은 GitHub 배포 성공 |

문구·문서·단순 시각 변경을 위해 무관한 테스트를 작성하거나 전체 플랫폼을 빌드하지 않는다. 필요한 관련 검사가 통과하면 새 변경이나 실패 없이 검증 범위를 계속 넓히지 않는다. 전체 테스트 모음, 전체 Firebase 계약 검사, 모든 플랫폼 빌드는 개별 기능 개발의 관성적인 완료 조건이 아니다.

## mock, 에뮬레이터, 실제 연결의 구분

- mock·fake 저장소를 사용하는 유닛·위젯 테스트는 정해진 응답에 대한 앱 동작을 검증한다. 실제 인증, callable 계약, 권한, 저장, 네트워크를 통과했다고 주장하지 않는다.
- Firebase 에뮬레이터에서 실제 callable 구현과 규칙을 실행한 결과는 로컬 통합 증거다. 개발 Firebase 또는 운영 Firebase에서 성공한 결과로 부르지 않는다.
- 개발 Firebase에 연결한 경우 프로젝트 ID, 서버 리비전, 앱 빌드와 실행한 흐름을 기록한다. 운영 성공이나 스토어 배포 앱의 성공으로 확대하지 않는다.
- 실제 앱 저장 흐름을 바꿨다면 앱에서 실제 callable을 호출하여 저장하고 재조회한 증거가 필요하다. 테스트에서 DB에 직접 문서를 넣거나 callable을 mock 응답으로 대체한 것만으로 앱 저장 흐름을 검증했다고 보지 않는다.
- 필요한 환경이 없어 이 확인을 수행하지 못했다면 `미확인`으로 인계하고 누락된 조건을 적는다. 필수 사용자 흐름이 미확인인 상태를 검증 완료로 보고하지 않으며, 통합 담당자는 배포 전에 그 공백을 해소해야 한다.

개발·테스트 환경과 테스트 계정을 우선 사용한다. 이 절차는 운영 데이터 생성·수정·삭제나 배포의 별도 권한을 부여하지 않는다. 증거에는 토큰·개인정보·비밀키를 포함하지 않는다.

## 검증 결과 인계

PR에는 다음 정보를 담는다. 표·목록 등 표현 형식은 자유롭다.

- 변경한 사용자 동작과 범위
- 검증한 커밋, 환경, 앱 빌드 및 관련 서버 리비전
- 실행한 명령 또는 재현 절차와 결과
- 테스트 유형 및 실제 외부 연결 여부: mock, 로컬 에뮬레이터, 개발 Firebase 등
- 로그·스크린샷·실행 링크 등 결과를 확인할 수 있는 증거
- 미실행·실패·미확인 항목과 그 이유, mock의 한계
- 서버·웹과 모바일에 각각 미치는 영향, 통합 시 필요한 주의점

`통과`, `실패`, `미실행`, `해당 없음`을 구분한다. 단순히 “테스트 완료”라고 쓰거나 CI가 예약·진행 중인 상태를 통과로 쓰지 않는다. 커밋 전에 확인했다면 검증 당시 기준 커밋과 포함된 미커밋 변경을 적고, 최종 인계 커밋에 같은 변경이 포함되는지 확인한다.

구현 완료, 기능 검증 완료, PR 제출, 통합 검증 통과, 배포 완료는 서로 다른 상태다. 스토어 업로드 완료도 사용자에게 공개 설치 가능한 상태와 다르다.

## 결과 재사용과 재검증

담당자나 단계가 바뀌었다는 이유만으로 같은 검사를 다시 실행하지 않는다. 검증 대상 코드, 의존성·설정, 실행 환경이 여전히 유효한지 확인하고 기존 결과를 재사용한다.

다음 경우에는 영향을 받는 범위만 다시 검증한다.

- 관련 코드 또는 의존성·설정·환경이 변경됨
- 충돌 해결이나 다른 기능과의 결합으로 동작이 달라질 수 있음
- 새 실패가 발견되거나 이전 결과·증거가 불완전함

재검증할 때는 이유와 범위를 적는다. 예를 들어 VM의 유닛 테스트 결과가 브라우저 런타임이나 iOS 실기기 결과를 대신하지 않는다. 실패한 검사를 삭제하거나 기존 클라이언트 계약을 제거하여 통과시키지 않는다.

## main 통합 검증과 배포 조건

실제 `main` 배포 대상 커밋에서 필수 통합 검증을 한 번 수행하고, 서버·웹 배포가 그 성공 결과에 의존하도록 한다. PR에서 제출한 기능 증거와 `develop`의 리뷰는 이 배포 조건을 대체하지 않는다.

- 통합 검증 실패·취소·미실행 또는 대상 커밋 불일치이면 배포를 시작하지 않는다.
- 실패를 수정한 새 후보는 영향을 받는 기능 검증을 갱신하고 해당 후보의 필수 통합 검증을 통과해야 한다. “한 번”은 실패 후 재검증을 생략하라는 뜻이 아니다.
- 서버·규칙 배포는 [기존 설치 클라이언트 호환성](released-client-compatibility.md)의 지원 계약을 유지해야 한다. 이 정책은 지원 버전의 축소나 기존 계약 검사의 삭제를 허용하지 않는다.
- 서버·웹 배포가 모바일 빌드·스토어 업로드를 자동으로 일으키지 않게 분리한다. 모바일 출시가 필요한 경우에만 수동 실행한다.
- 모바일 수동 실행도 대상 소스 커밋의 유효한 통합 검증 결과와 필요한 서버 배포·호환성을 확인해야 한다. 같은 커밋에 대한 무거운 통합 검증을 모바일 워크플로마다 다시 실행할 필요는 없지만, 플랫폼 빌드·서명·업로드 자체는 별도로 성공해야 한다.
- 수동 실행, 예전 성공 실행, 브랜치 이름만으로 배포 조건을 우회하지 않는다. 실제 배포 소스와 확인한 결과의 대상 커밋이 일치해야 한다.

### 이번 변경과 후속 범위

이번 변경은 PR의 무거운 자동 검증과 develop push의 자동 검증·개발 배포를 없애고, main 배포 전 검증과 수동 개발 환경 배포를 유지한다. PR의 기존 필수 check 이름인 `firebase-required`는 가벼운 인계 정보·공백 검사에 사용한다. 실제 통합 검사 성공을 뜻하지 않으며 운영 배포는 main workflow의 별도 검증·manifest 집계를 계속 요구한다.

PR 양식의 세 섹션과 `검증한 커밋:`에 현재 PR head SHA(7자리 이상)를 적는다. 새 커밋으로 검증 대상이 바뀌면 결과의 유효성을 확인하고 기록을 갱신한다. 자동 검사는 기록의 존재와 대상만 확인하므로 리뷰어는 실제 명령·결과·미확인 사항을 읽어야 한다.

모바일 workflow는 이번에 수동 실행으로 전환한다. 기존 동일 SHA backend 배포 확인과 모바일 내부 Flutter 검사는 아직 유지한다. 현재 운영 backend와 새 모바일의 호환성 증빙을 분리하고 공통 테스트 결과를 재사용하는 후속 작업이 끝나기 전까지 이 의존성과 중복 검사를 제거하지 않는다. 따라서 이번 변경은 자동 실행을 분리한 것이며 모바일의 backend 의존성을 완전히 없앤 상태는 아니다.

워크플로 변경 적용 여부는 PR 반영 상태와 실제 GitHub 실행 조건으로 확인한다. 이전 브랜치 정의로 이미 시작한 실행과 새 정책으로 시작한 실행도 구분한다.

## STA-184 앱 E2E의 현재 상태

이 정책 작성 시점에 STA-184의 실제 앱 E2E 자동화는 Todo 계획 상태이며, 이 문서나 정책 변경으로 구현되는 기능이 아니다. 존재하지 않는 E2E 명령·실행 결과를 적거나 계획된 시나리오를 이미 통과했다고 보고하지 않는다.

자동화가 준비되기 전에도 실제 앱 저장 등 필수 흐름의 확인은 생략하지 않는다. 현재 실행 가능한 관련 검사와 개발·테스트 환경의 실제 앱 조작 증거를 남기고, 자동화되지 않은 범위는 명시한다. STA-184가 구현되면 실제 실행 가능한 시나리오와 명령, 적용 범위를 근거로 이 문서를 갱신한다.
