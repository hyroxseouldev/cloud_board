# 기능 검증과 배포 인계

기능 개발 담당자가 변경한 기능을 검증하고 결과를 인계한다. PR과 `develop`에서는 가벼운 인계 확인과 코드·증거 리뷰를 수행한다. `main` push는 통합만 하며 배포하지 않는다. 개발 `dev/vX.Y.Z-N` 태그는 개발 웹·서버·모바일 QA를 시작하고, 운영 `vX.Y.Z` 태그는 필수 통합 CI를 기본으로 실행한다. 수동 운영 릴리즈에는 사유를 기록하는 명시적 CI 생략 옵션이 있다. 서버 배포, 웹 배포, 모바일 업로드와 CI 생략의 결과는 각각 구분한다.

이 문서는 STA-181의 작업·검증 정책이다. 문서를 작성하거나 PR을 제출한 사실만으로 GitHub 자동 실행이 변경되지는 않는다. 워크플로 변경이 대상 브랜치에 반영되고 트리거·배포 의존 조건이 확인되어야 해당 자동화가 적용된 것이다. 저장소의 필수 검사 설정과도 일치하는지 확인해야 한다.

## 단계별 책임

| 단계 | 담당과 확인 내용 | 다음 단계로 전달할 것 |
| --- | --- | --- |
| 기능 개발 | 개발 담당자가 변경한 정상 흐름·실패 처리·기존 호환성을 관련 범위에서 검증 | 코드, 검증 대상 커밋, 실행 명령·결과·증거, 한계 |
| 기능 PR / develop | 코드·기능 검증 증거를 리뷰하고 기능 PR을 squash 병합 | 해결된 리뷰, 필요한 경우 영향 범위 재검증, 통합 후보 |
| 통합 승격 PR | develop에서 main으로 한 번 merge | 포함한 기능 PR, 인계 대상 SHA와 재사용할 증거 |
| main 통합 | 변경 통합과 표시 버전 확정, push 자체는 배포하지 않음 | 버전 확정 커밋, 배포 의도·태그·CI 정책 |
| 개발 태그 | main 이력의 `dev/vX.Y.Z-N`에서 개발 Firebase 웹·백엔드와 개발 앱(`.dev`) 테스트 경로 | 버전 일치·모바일 스토어 준비·환경·빌드·산출물 검사, 고정 SHA와 실제 실행 결과 |
| 릴리즈 태그 | main 이력의 고정 SHA에 앱 버전과 일치하는 vX.Y.Z 태그를 만들고 기본 필수 통합 CI | 동일 태그 SHA의 검증 결과 또는 명시적 수동 생략 기록, 운영 배포 산출물 |
| 운영 서버 / 웹 | 태그의 CI 성공 또는 사유 있는 수동 생략을 확인하고 범위별 배포 | 배포 커밋·태그·환경·결과·생략 여부 |
| 모바일 QA | 기존 개발 앱(`.dev`)·개발 Firebase, 스토어 준비·서명·산출물·개발 환경 연결 확인 | 고정 소스 SHA, TestFlight·Play 내부 업로드 결과와 QA 한계 |
| 모바일 정식 업로드 | 태그 SHA의 CI 증거 또는 명시적 생략 기록과 운영 서버 호환성을 확인 | 고정 태그·커밋, CI 상태, 서명·실제 산출물·업로드 결과 |

PR과 `develop`에서 무거운 전체 테스트·계약 검사·모바일 빌드를 자동으로 반복하지 않는 것이 목표다. 필요한 가벼운 형식 검사나 증거 확인은 기능 검증을 대체하지 않는다. 개발 환경을 갱신했다는 사실도 통합 검증이나 운영 배포 성공의 증거가 아니다.

## 브랜치와 승격

기본 흐름은 `기능 브랜치 → develop(squash) → main(통합 merge·버전 확정) → dev/vX.Y.Z-N(개발 배포) → vX.Y.Z(운영 릴리즈)`다. 기능 PR은 `develop`에 한 번 squash 병합하고, 통합할 기능을 모은 `develop`에서 `main`으로 승격 PR을 열어 한 번 merge한다. main push 자체는 개발·운영 어느 쪽도 배포하지 않는다. 같은 기능 브랜치를 `develop`과 `main`에 각각 PR로 올리지 않는다. iOS·Android는 공통 Flutter 기능을 함께 개발하며, 플랫폼 고유 차이만 관련 검사로 확인한다.

통합 담당자 한 명이 기준 브랜치 갱신, 충돌 해결, 승격을 소유한다. strict 필수 체크 때문에 최신 기준 브랜치 반영이 필요하면 한 번 정리하고 PR 인계 SHA와 증거를 갱신한다. 사용자가 별도로 지정한 긴급 수정은 그 범위를 따르되, 수정이 다음 정식 배포에서 사라지지 않도록 통합 담당자가 다른 브랜치 반영까지 정리한다.

### 표시 버전 확정과 태그

main에서 `pubspec.yaml`의 표시 버전을 먼저 확정해 커밋하고 그 SHA에 태그를 만든다. 같은 표시 버전의 재빌드마다 버전을 올리지 않으며 플랫폼별 빌드 번호는 자동 할당한다. 개발 태그의 `N`은 같은 표시 버전의 개발 배포 차수를 구분한다. 변경된 후보는 새 개발 태그를 사용하고 기존 태그를 이동·삭제해 재사용하지 않는다. main의 버전 확정 변경은 develop에도 역동기화한다.

버전 확정 커밋은 다음과 같이 준비한다. 본문의 태그와 CI 항목은 배포 의도이며 실제 실행 결과는 별도로 기록한다.

```text
release: CloudBoard 1.2.2 - 주요 변경

Version: 1.2.2
Changes: 주요 변경 요약
Deployment intent: 개발 확인 후 운영 릴리즈 예정
Development tag: dev/v1.2.2-1
Production tag: v1.2.2
CI policy: 개발 전체 CI 없음; 운영 skip_ci=false(기본), 생략 시 skip_ci=true와 사유 기록
```

**Start production release** 메뉴는 서버·웹·모바일 대상 선택과 운영 태그 생성·실행을 담당하며 `pubspec.yaml`을 자동 변경하지 않는다. 개발 배포는 버전 확정 커밋이 main에 반영된 후 해당 SHA로 태그를 push한다.

```sh
git tag dev/v1.2.2-1 <버전-확정-main-SHA>
git push origin refs/tags/dev/v1.2.2-1
```

### 앱 업데이트 소식 작성

앱 소식은 **해당 플랫폼의 직전 실제 배포 main SHA → 이번 후보 main SHA**의 `git diff`로 포함된 변경을 확인해 작성한다. 현재 HEAD나 이전 main 한 커밋만 비교하면 배포 사이에 쌓인 변경을 빠뜨릴 수 있다. iOS·Android/TV·웹의 직전 배포 시점이 다르면 비교 기준도 각각 기록한다.

차이에서 사용자에게 영향을 주는 내용을 추려 자연스러운 문구로 `release-notes/current.json`에 적고 후보 표시 버전과 함께 커밋한다. 원시 커밋 제목·본문이나 개발 로그를 앱에 그대로 노출하지 않는다. 배포 전에는 후보 소식이며, 실제 해당 플랫폼 배포·업로드 성공과 빌드 증거가 확인된 후에만 소식 조건을 연결한다. 개발 태그 QA는 운영 소식을 게시하지 않는다. 이 절차는 소식을 자동으로 생성하는 기능을 추가하지 않는다. 상세 형식은 [앱 업데이트 소식](../release-notes/README.md)을 따른다.

## 기능 개발 단계의 완료 기준

변경한 기능에 대해 다음 세 가지를 확인한다. 관련 없는 경우에는 그 이유를 적는다.

1. **정상 흐름:** 사용자가 해당 동작을 시작하여 기대하는 결과까지 도달한다. 값이 저장되는 기능은 다시 읽었을 때 결과가 유지되는지 포함한다.
2. **실패 처리:** 이번 변경과 관련된 입력 오류, 권한 거부, 네트워크 실패, 재시도·취소 등에서 잘못된 성공 안내나 데이터 손상이 발생하지 않는다. 모든 기능에 모든 장애 조합을 강요하지 않는다.
3. **기존 호환성:** 변경의 영향을 받는 기존 화면·데이터·클라이언트 동작이 유지된다. 서버·규칙·직렬화 변경은 현재 배포된 앱·TV 및 기존 웹 탭이 사용하는 계약을 확인한다.

검증 범위는 실제 위험과 변경에 비례한다.

| 변경 유형 | 기능 단계에서 필요한 확인 예 | 이것만으로 주장할 수 없는 것 |
| --- | --- | --- |
| 문구·문서 | 변경 내용, 링크, 의도하지 않은 수정 확인 | 앱 전체 회귀 검증 |
| 단순 시각 변경 | 관련 화면의 배치·잘림·상태 확인, 영향을 받는 크기나 플랫폼 확인 | 모든 기기의 완전한 동일성 |
| 상태·계산·검증 로직 | 변경한 분기와 경계값의 관련 유닛 테스트 | 실제 SDK·네트워크 성공 |
| 화면 상호작용 | 관련 위젯 테스트 또는 실제 앱 조작, 실패 상태·기존 흐름 확인 | mock 너머의 서버 저장 성공 |
| 앱 저장·동기화 | 관련 로직 검사와 실제 앱→실제 callable→저장→재조회 확인 | 실제로 사용하지 않은 환경의 성공 |
| 서버·접근 규칙·계약 | 영향받는 허용·거부·기존 클라이언트 계약의 집중 검사 | 모든 설치 버전·실기기의 동작 |
| 워크플로·도구 | 변경한 설정의 빠른 유효성 검사와 조건·실패 경로 확인 | 아직 실행하지 않은 GitHub 배포 성공 |

문구·문서·단순 시각 변경을 위해 무관한 테스트를 작성하거나 전체 플랫폼을 빌드하지 않는다. 필요한 관련 검사가 통과하면 새 변경이나 실패 없이 검증 범위를 계속 넓히지 않는다. 전체 테스트 모음, 전체 Firebase 계약 검사, 모든 플랫폼 빌드는 개별 기능 개발의 관성적인 완료 조건이 아니다.

## mock, 에뮬레이터, 실제 연결의 구분

- mock·fake 저장소를 사용하는 유닛·위젯 테스트는 정해진 응답에 대한 앱 동작을 검증한다. 실제 인증, callable 계약, 권한, 저장, 네트워크를 통과했다고 주장하지 않는다.
- Firebase 에뮬레이터에서 실제 callable 구현과 규칙을 실행한 결과는 로컬 통합 증거다. 개발 Firebase 또는 운영 Firebase에서 성공한 결과로 부르지 않는다.
- 개발 Firebase에 연결한 경우 프로젝트 ID, 서버 리비전, 앱 빌드와 실행한 흐름을 기록한다. 운영 성공이나 스토어 배포 앱의 성공으로 확대하지 않는다.
- 실제 앱 저장 흐름을 바꿨다면 앱에서 실제 callable을 호출하여 저장하고 재조회한 증거가 필요하다. 테스트에서 DB에 직접 문서를 넣거나 callable을 mock 응답으로 대체한 것만으로 앱 저장 흐름을 검증했다고 보지 않는다.
- 필요한 환경이 없어 이 확인을 수행하지 못했다면 `미확인`으로 인계하고 누락된 조건을 적는다. 필수 사용자 흐름이 미확인인 상태를 검증 완료로 보고하지 않으며, 통합 담당자는 배포 전에 그 공백을 해소해야 한다.

개발·테스트 환경과 테스트 계정을 우선 사용한다. 이 절차는 운영 데이터 생성·수정·삭제나 배포의 별도 권한을 부여하지 않는다. 증거에는 토큰·개인정보·비밀키를 포함하지 않는다.

## 검증 결과 인계

PR 양식의 세 섹션은 유지하고, 각 섹션 안의 표·목록 등 표현 형식은 자유롭게 사용한다.

- 변경한 사용자 동작과 범위
- 현재 PR 인계 대상 커밋, 실제 검사·증거의 커밋, 환경, 앱 빌드 및 관련 서버 리비전
- 실행한 명령 또는 재현 절차와 결과
- 테스트 유형 및 실제 외부 연결 여부: mock, 로컬 에뮬레이터, 개발 Firebase 등
- 로그·스크린샷·실행 링크 등 결과를 확인할 수 있는 증거
- 미실행·실패·미확인 항목과 그 이유, mock의 한계
- 서버·웹과 모바일에 각각 미치는 영향, 통합 시 필요한 주의점

`통과`, `실패`, `미실행`, `해당 없음`, 명시적인 `CI 생략`을 구분한다. 단순히 “테스트 완료”라고 쓰거나 CI가 예약·진행 중·생략인 상태를 통과로 쓰지 않는다. 커밋 전에 확인했다면 검증 당시 기준 커밋과 포함된 미커밋 변경을 적고, 최종 인계 커밋에 같은 변경이 포함되는지 확인한다.

기존 자동 검사와 호환되도록 `검증한 커밋:` 필드에는 현재 인계 대상 PR head SHA를 적는다. 이 필드가 확인됐다는 사실은 해당 SHA에서 모든 테스트를 새로 실행했다는 뜻이 아니다. `실제 검사·증거의 커밋 / 재사용 근거:`에는 실행 당시 SHA와 결과 링크를 적는다. 같으면 `위와 같음`으로 표시한다. squash·승격·기준 브랜치 갱신으로 SHA가 바뀌었으면 검증 대상 코드·의존성·설정·환경의 차이를 확인한 근거와 추가로 확인한 범위를 남긴다. 새 코드에 옛 테스트 결과의 SHA를 덮어써서 기록하지 않는다.

구현 완료, 기능 검증 완료, PR 제출, 통합 검증 통과, 배포 완료는 서로 다른 상태다. 스토어 업로드 완료도 사용자에게 공개 설치 가능한 상태와 다르다.

## 결과 재사용과 재검증

담당자나 단계가 바뀌었다는 이유만으로 같은 검사를 다시 실행하지 않는다. 검증 대상 코드, 의존성·설정, 실행 환경이 여전히 유효한지 확인하고 기존 결과를 재사용한다.

다음 경우에는 영향을 받는 범위만 다시 검증한다.

- 관련 코드 또는 의존성·설정·환경이 변경됨
- 충돌 해결이나 다른 기능과의 결합으로 동작이 달라질 수 있음
- 새 실패가 발견되거나 이전 결과·증거가 불완전함

재검증할 때는 이유와 범위를 적는다. 예를 들어 VM의 유닛 테스트 결과가 브라우저 런타임이나 iOS 실기기 결과를 대신하지 않는다. 실패한 검사를 삭제하거나 기존 클라이언트 계약을 제거하여 통과시키지 않는다.

## 개발·운영 태그 배포

`main` push는 배포하지 않는다. main 이력의 고정 SHA에 표시 버전과 일치하는 `dev/vX.Y.Z-N` 태그를 만들면 개발 Firebase `cloud-board-development`의 웹·백엔드 배포와 기존 개발 앱(`.dev`)의 TestFlight·Play 내부 테스트 경로를 실행한다. 모바일 QA도 개발 Firebase에 연결하며 스토어 준비가 확인된 경우에만 빌드·업로드한다. 전체 Flutter·Chrome·Firebase 계약 검사를 반복하지 않으며 환경, 빌드, 서명, 실제 산출물 확인은 유지한다. 개발 배포·플랫폼 업로드 실패를 각각 보고하고 운영 웹·서버 배포나 통합 검증 성공으로 해석하지 않는다.

운영 릴리즈는 `main` 이력에 포함된 SHA의 `vX.Y.Z` 태그에서 시작한다. 태그의 버전과 `pubspec.yaml`의 앱 버전이 일치해야 한다. 자동 태그 실행은 필수 통합 CI를 해당 태그 SHA에서 기본 실행하고 서버·웹 배포와 모바일 정식 업로드는 그 성공 결과를 사용한다. 모바일은 동일 SHA의 유효한 공통 검증 증거를 재사용한다. PR 인계 체크와 개발 태그 빌드는 이 조건을 대체하지 않는다.

수동 Firebase 태그 릴리즈 또는 수동 모바일 `release`는 `skip_ci=true`와 비어 있지 않은 `skip_ci_reason`을 지정해 무거운 CI를 생략할 수 있다. Firebase는 실제 배포 범위 `full`·`backend`·`rules`·`web`에서만 허용하며 main의 확인용 실행이나 `verify`, 모바일 QA에서는 거절한다. 생략된 앱 검사·수업 시작 회귀·Firebase emulator 계약 검사를 `통과`로 기록하지 않는다. 사유, 실행자, run/attempt, 소스 SHA와 태그를 감사 artifact/receipt에 남긴다. `validationMode: required`도 검증 요청을 뜻하며 자체로 테스트 성공 증거는 아니다.

새 운영 릴리즈는 main의 **Start production release**에서 `deploy_server`·`deploy_web`·`deploy_mobile`을 독립 선택한다. 기본값은 모두 해제이며 하나 이상 선택해야 한다. 서버는 Functions와 데이터 규칙·인덱스(`backend`), 웹은 Hosting(`web`), 둘을 함께 선택하면 `full`이다. 모바일만 선택하면 `verify`로 CI를 수행하고 서버·웹을 배포하지 않은 채 iOS와 Android/TV 업로드로 이어진다. 함께 선택한 경우 서버·웹 배포가 모두 성공한 뒤 모바일이 실행된다. 선택 조합은 [운영 릴리즈 정책](operations/release-policy.md#select-server-web-and-mobile-independently)을 따른다.

서버·웹을 선택한 새 릴리즈는 `skip_ci`와 필요한 사유를 선택할 수 있다. 모바일만 선택한 `verify` 경로는 CI를 생략할 수 없으며, 별도 수동 모바일 `release`의 감사 기록을 남기는 생략 옵션은 유지한다. 이 메뉴는 고정 SHA의 새 운영 태그를 만들고 선택한 정책으로 한 번 실행하며 버전은 변경하지 않는다. 기존 운영 태그 재시도는 해당 태그의 Firebase workflow에서 지정하며 `deploy_mobile` 기본값은 `false`다. 예전 태그의 workflow에는 새 입력이 없을 수 있다. 운영 태그를 외부에서 직접 push하면 기본 CI·배포 이력에 따른 서버/웹 범위·모바일 후속 업로드가 자동으로 시작하며, 별도로 수동 실행했다고 이미 시작한 자동 실행이 생략 모드로 바뀌지는 않는다.

모바일 자동 후속 실행은 해당 Firebase 실행의 감사 artifact에서 `mobileUploadRequested=true`를 확인한다. 해시와 소스 SHA·태그·run/attempt를 검증하고, 과거 기록에 선택 필드가 없으면 모바일 빌드·업로드를 건너뛴다. artifact가 없거나 만료·불일치하면 차단한다. 서버·웹만 선택해도 모바일의 짧은 preflight 실행은 표시될 수 있지만 SDK 설치·빌드·업로드는 하지 않는다.

모바일을 먼저 설치하고 서버만 나중에 배포할 수 있다. 현재 운영 backend receipt와 후보의 서버·규칙 지문이 같으면 기존 확인을 재사용한다. 다르면 `mobile-backend-compatibility` CI에서 현재 운영 서버 사본에 후보 앱의 직렬화 데이터와 관련 callable/규칙 계약을 재생하고, 현재 서버에서의 앱 동작 및 새 기능의 대기·비활성 테스트를 통과해야 한다. 후보와 운영 서버에 맞는 검증 명세를 `release-notes/mobile-compatibility.json`에 관리한다. 단순 승인 체크박스나 `skip_ci`는 이 증거를 대신하지 않는다. SDK 설치 전과 업로드 직전에 실제 운영 receipt·지문과 증거의 앱 SHA·태그·run/attempt를 확인한다. 실제 운영 데이터를 변경하는 검사는 아니다. 상세 절차와 검증 범위는 [모바일 먼저 배포](operations/mobile-first-release.md)를 따른다.

모바일에 사용한 동일 소스의 서버를 나중에 올릴 때는 기존 태그의 Firebase workflow에서 `scope=backend`, `deploy_mobile=false`를 선택한다. 소스가 달라지면 새 후보·일치하는 새 태그가 필요하다. 기존 앱·TV·열린 웹과의 호환성을 유지하며 태그를 옮겨 재사용하지 않는다.

생략해도 태그 고정·SHA·main 이력·버전·운영 배포 대상, 빌드·서명·환경·번호·실제 산출물·manifest 해시·배포 후 smoke는 확인한다. 웹 빌드는 필요한 범위에서 계속 실행하며 서버·웹 배포 범위를 넓히지 않는다. 모바일의 현재 운영 backend receipt와 지문 일치 또는 실제 호환성 테스트 증거 확인도 유지한다.

- 명시적 수동 CI 생략이 없으면 통합 검증 실패·취소·미실행 시 운영 배포를 시작하지 않는다. 태그·대상 커밋 불일치는 생략 여부와 관계없이 차단한다.
- 실패를 수정한 새 후보는 영향을 받는 기능 검증을 갱신하고 해당 후보의 CI 결과 또는 명시적 생략 기록을 남긴다. 생략 선택이 기존 실패를 통과로 바꾸지는 않는다.
- 서버·규칙 배포는 [기존 설치 클라이언트 호환성](released-client-compatibility.md)의 지원 계약을 유지해야 한다. 이 정책은 지원 버전의 축소나 기존 계약 검사의 삭제를 허용하지 않는다.
- 태그에서 시작한 서버·웹·모바일 작업은 같은 소스 SHA를 사용하고 각 결과를 구분한다. 한 플랫폼 실패를 다른 플랫폼의 성공으로 덮지 않는다. 수동 복구나 재실행도 태그·SHA·필수 증거 조건을 우회하지 않는다.
- 모바일 정식 모드 `release`는 태그 SHA의 유효한 통합 검증 증거 또는 명시적 생략 기록과 운영 서버 호환성을 확인한다. 공통 결과를 모바일 워크플로마다 다시 만들 필요는 없지만, 플랫폼 빌드·서명·실제 산출물 검사·업로드는 별도로 성공해야 한다.
- 수동 실행, 예전 성공 실행, 브랜치 이름만으로 배포 조건을 우회하지 않는다. 실제 배포 소스와 확인한 결과의 대상 커밋이 일치해야 한다.

## 모바일 QA와 정식 업로드

자동 경로는 `dev/vX.Y.Z-N` 태그의 모바일 QA와 `vX.Y.Z` 태그의 운영 릴리즈다. 수동 경로에서는 신뢰되는 기본 브랜치의 workflow에서 `release_mode: qa | release`와 `source_ref`를 선택한다. QA도 main 이력에 포함되고 `pubspec.yaml` 표시 버전과 일치하는 개발 태그를 요구하며 main/develop 브랜치나 임의 SHA만으로 실행하지 않는다. 정식 모드는 버전과 일치하는 운영 태그를 요구한다. 빌드할 소스는 시작 시 한 번 해석한 SHA로 고정하고, 검사·빌드·업로드 및 재확인에 같은 SHA를 사용한다. 도중에 이동한 브랜치의 최신 코드로 바꾸지 않는다.

| 모드 | 확인할 것 | 성공이 의미하는 것 |
| --- | --- | --- |
| `qa` | 기존 개발 앱(`.dev`)·개발 Firebase, 스토어 준비·서명·버전·실제 산출물, 업로드 결과 | 개발 앱의 TestFlight·Play 내부 테스트용 산출물 또는 업로드. 전체 CI 통과·정식 출시를 뜻하지 않음 |
| `release` | 릴리즈 태그 SHA의 CI 증거 또는 명시적 생략 기록, 운영 서버 호환성, 서명·버전·실제 산출물, 업로드 결과 | 해당 운영 후보의 업로드 완료. CI 생략·스토어 심사·공개 완료와는 별도 |

QA는 기존 개발 앱 `com.sunmkim.cloudboard.dev`·`development` flavor·`cloud-board-development`를, release는 `com.sunmkim.cloudboard`·`production` flavor·`cloud-board-stationd`를 사용한다. `testflight` / `google-play` GitHub Environment의 계정 인증은 사용할 수 있지만 앱별 스토어 등록·서명 접근은 각각 확인한다. 빌드 번호와 업로드 동시 실행 그룹도 앱별로 분리한다. 실제 AAB/IPA의 Firebase SDK·컴파일된 환경·서명·버전을 검사한다.

개발 Firebase 앱 설정과 iOS 개발 앱의 기기 설치용 서명은 이미 준비됐다. `.dev` 스토어 등록·배포용 서명·업로드 준비는 별도 미확인이며 개발 Play 번호 기준 파일도 없다. 실제 개발 앱의 스토어 상태와 번호 이력을 확인하고 각 Environment에 `MOBILE_DEVELOPMENT_READY=true`를 설정한 뒤 QA 스토어 경로의 빌드를 허용한다. 준비 전에는 차단 상태를 보고하고 SDK 설치·빌드·업로드를 시작하지 않는다. 운영 Play 기준 파일을 개발 앱에 재사용하지 않는다.

개발 웹·서버와 모바일 QA는 같은 Firebase를 사용한다. QA 업로드는 운영 backend receipt를 요구하지 않고 운영 설치 클라이언트 계약 추적에서 제외한다. 과거 실제 운영 Firebase 연결 QA 기록은 보존한다. release는 태그 CI 성공 또는 명시적 생략 기록과 현재 운영 서버 호환성 증거를 확인하며 개발 배포 성공으로 대체하지 않는다.

모바일 수동 release의 CI 생략은 Firebase CI 생략 실행을 먼저 요구하지 않는다. 자동으로 이어지는 모바일 release가 Firebase의 생략 기록을 사용한다면 그 실행의 run/attempt·SHA·태그를 확인하고 감사 정보를 이어 기록한다. 두 경로 모두 백엔드 호환성 검사는 유지한다.

개발·운영 앱은 서로 다른 앱 ID의 기존 샌드박스를, 웹은 별도 origin을 사용한다. 개발 빌드를 스토어 일반 공개 후보로 승격하지 않으며, 공개에는 production flavor의 검증된 release 산출물을 사용한다.

QA 업로드 성공은 정식 배포 성공 소식 발행, 최소 지원 버전 승격, 서버·웹 배포를 일으키지 않는다. 이들 작업은 각 정식 배포 정책에서 별도로 판단한다. 업로드와 Apple·Google의 후속 처리·심사·공개 상태도 구분해 보고한다.

운영 릴리즈에는 `vX.Y.Z` 태그가 필요하다. 태그 이름 자체는 검증 성공이 아니며 SHA·검증 결과·산출물을 연결해야 한다. 태그는 main 이력과 앱 버전을 확인한 뒤 만들고, 이미 사용한 태그를 이동·삭제하여 재사용하지 않는다. 수정한 후보는 적절한 새 버전·태그로 진행한다.

### 자동화 적용 상태와 후속 범위

PR과 develop 단계는 가벼운 인계 확인을 유지하고 main push는 통합만 한다. 개발 빌드·배포는 개발 태그에서 시작하며 운영 필수 CI는 자동 운영 태그 시점에 수행한다. 수동 운영 릴리즈의 CI 생략은 별도 감사 기록으로 남긴다. PR의 기존 필수 check 이름인 `firebase-required`는 인계 정보·공백 검사이며 실제 통합 검사 성공을 뜻하지 않는다. 운영 배포는 태그 SHA의 검증 또는 명시적 생략 기록과 manifest 집계를 별도로 요구한다.

PR 양식의 세 섹션과 `검증한 커밋:`에 현재 PR head SHA(7자리 이상)를 적는다. 새 커밋으로 인계 대상이 바뀌면 결과의 유효성을 확인하고 기록을 갱신한다. 자동 검사는 기록의 존재와 대상만 확인하므로 리뷰어는 실제 명령·결과·증거 SHA·미확인 사항을 읽어야 한다. 과거 한 번의 실행 시간은 이후 PR이나 배포의 소요 시간 보장이 아니다.

개발 태그의 웹·서버 자동화와 앱 QA, 운영 태그 릴리즈, 고정 SHA는 실제 workflow와 gate 구현을 함께 검토한다. 개발 WIF의 개발 태그 허용 조건과 개발 모바일 앱의 스토어 등록·서명·업로드 준비도 따로 확인한다. PR만 작성됐거나 브랜치에 코드만 추가된 상태를 원격 정책 적용·배포 완료로 보고하지 않는다. 공통 검증 재사용도 원본 증거와 대상의 일치 여부를 확인해야 하며, 증거 연결 없이 검사를 삭제하지 않는다.

워크플로 변경 적용 여부는 PR 반영 상태와 실제 GitHub 실행 조건으로 확인한다. 이전 브랜치 정의로 이미 시작한 실행과 새 정책으로 시작한 실행도 구분한다.

## STA-184 앱 E2E의 현재 상태

이 정책 작성 시점에 STA-184의 실제 앱 E2E 자동화는 Todo 계획 상태이며, 이 문서나 정책 변경으로 구현되는 기능이 아니다. 존재하지 않는 E2E 명령·실행 결과를 적거나 계획된 시나리오를 이미 통과했다고 보고하지 않는다.

자동화가 준비되기 전에도 실제 앱 저장 등 필수 흐름의 확인은 생략하지 않는다. 현재 실행 가능한 관련 검사와 개발·테스트 환경의 실제 앱 조작 증거를 남기고, 자동화되지 않은 범위는 명시한다. STA-184가 구현되면 실제 실행 가능한 시나리오와 명령, 적용 범위를 근거로 이 문서를 갱신한다.

## 정리 후 워크플로 역할

| 워크플로 | 실행 시점과 역할 |
| --- | --- |
| `development-handoff.yml` | PR에서 인계 기록·공백 확인만 수행. 필수 `firebase-required` 상태 이름 유지 |
| `firebase-development.yml` | `dev/vX.Y.Z-N` 태그 또는 해당 태그 재시도에서 개발 웹·서버 배포 |
| `firebase-hosting-merge.yml` | `vX.Y.Z` 운영 CI·범위별 배포, 또는 main의 수동 `scope=verify` 진단 |
| `testflight-main.yml`, `google-play-main.yml` | 개발 태그 QA 및 운영 릴리즈의 플랫폼별 빌드·서명·업로드 |
| `start-production-release.yml` | main에서 새 운영 태그, 서버·웹·모바일 대상과 CI 선택을 받아 릴리즈를 한 번 시작 |
| `class-start-regressions.yml` | 운영 검증에서 재사용 호출. PR·develop 자동 실행 없음 |
| `app-update-news.yml` | 운영 완료 이벤트와 수동 복구에서 실제 배포 증거를 확인해 소식 게시. 별도 PR·develop 검사와 게시마다의 자체 테스트 제거 |
| `firebase-release-monitor.yml` | 시간별 운영 규칙·저장 진단·보호 설정 관찰. 배포하지 않음 |
| `native-development-readiness.yml` | 요청할 때만 개발 앱 스토어 등록·접근 상태 조회 |

중복 수동 `operations-compatibility.yml`은 제거한다. 앱 전체 테스트, `operations-history` emulator 계약, legacy 빌드·소스·릴리즈 검사는 기존 Firebase workflow의 `scope=verify`에서 유지한다. 수동 진단은 main을 선택하고 해당 커밋의 `confirm_sha`를 입력하며 실제 운영 배포는 하지 않는다. 이미 수동 전용이던 파일을 제거한 것이므로 이 삭제 자체가 자동 실행 시간을 줄이지는 않는다. 새 개발·운영 태그 정책과 CI 생략 선택은 유지한다.
