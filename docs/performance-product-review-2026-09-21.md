# CloudBoard 성능·제품 완성도 개선 분석

작성일: 2026-09-21  
기준: `develop` · `1376110`  
범위: 소스·DB 규칙·배포 워크플로 분석. 이번 작업은 분석 문서만 작성했다. 앱 코드, 운영 DB, 배포 설정은 변경하지 않았다.

## 1. 판단

다음 작업은 **이미지 편집·저장 속도 개선**과 **여러 기기에서 수업을 안전하게 운영하는 흐름 완성**에 집중하는 것이 좋다. 백엔드 교체나 전면 리팩토링보다 지금 구조에서 남은 데이터 처리와 실패 복구를 보완하는 편이 적절하다.

특히 다음 세 가지는 단순 속도 문제가 아니다.

1. 예약 실행권을 얻은 뒤 시작에 실패하면 그 회차를 재시도하지 못할 수 있다.
2. 워크아웃 본문 저장에는 편집 시작 버전 검사가 없어 다른 기기의 수정을 덮어쓸 수 있다.
3. 수업 준비 화면의 이미지 준비 완료는 컨트롤러 기준이며 TV의 준비 완료를 보장하지 않는다.

위 내용은 코드로 확인한 실패 가능 경로다. 실제 운영에서 발생한 빈도나 재현 결과를 뜻하지 않는다. 실기기 프로파일·운영 사용량·사용자 행동 분석은 이번에 수행하지 않았으므로 개선율과 절감 비용을 수치로 단정하지 않는다.

## 4. 상세 분석

### A. 예약 실패 복구와 수업 시작 충돌

**근거**

- `lib/src/app/feature/operations/presentation/controllers/store_operations_controller.dart:130`에서 회차를 선점하고, 이후 `start()`를 호출한다.
- `lib/src/app/feature/operations/data/datasources/store_operations_realtime_data_source.dart:88`은 `lastOccurrenceKey`가 같으면 선점을 거절한다. 시작 성공·실패·선점 만료 상태는 분리되어 있지 않다.
- `lib/src/app/feature/playback/data/datasources/playback_realtime_data_source.dart:145`는 새 `activeSession`을 다중 경로 update로 기록한다. 기존 세션을 조건부로 확인하는 시작 트랜잭션은 아니다. `database.rules.json:25`에도 다른 활성 세션으로의 교체 자체를 막는 조건은 없다.
- `lib/src/app/feature/device/presentation/views/device_mode_home_screen.dart:35`의 화면 효과가 20초 주기 실행기를 소유한다. `operations_metrics.dart:87`의 실행 유예는 5분이다.

**위험**: 선점 후 네트워크 오류·설정 조회 실패가 나면 같은 회차가 제외될 수 있다. 두 컨트롤러가 동시에 다른 수업을 시작하면 사전 조회만으로 경쟁을 막기 어렵다. 앱이 종료된 동안의 무인 예약도 이 실행기만으로 보장할 수 없다. 화면의 “온라인 디스플레이에서 자동으로 시작” 안내는 이 제약을 충분히 설명하지 않는다(`store_operations_screen.dart:349`).

**제안**: 회차별 `pending → starting → started / failed / skipped`, 만료 가능한 실행권, 고정 sessionId를 둔다. 응답 유실 시 같은 ID로 실제 시작 여부를 확인한 뒤 재시도한다. 계정의 수업 시작은 서버에서 원자적으로 선점하며, 다른 수업이 진행 중이면 교체 의사를 명시적으로 받는다. 예약 삭제·수정 시 회차 버전도 확인한다. 앱 종료 후 실행까지 제품 요구사항으로 확정한다면 서버 실행기로 이전하되 매장 시간대와 오프라인 TV 처리까지 포함한다.

**완료 기준**: 선점 직후 종료, 서버 반영 후 응답 유실, 컨트롤러 2대 동시 시작, 예약/수동 시작 충돌에서도 동일 회차 최대 1회 실행. 실패는 화면에 남고 안전하게 재시도할 수 있어야 한다.

### B. 워크아웃 본문 동시 편집 보호

**근거**: `workout_firestore_data_source.dart:140`은 트랜잭션에서 기존 문서를 읽지만 호출자가 편집을 시작한 버전과 비교하지 않는다. 읽은 기존 값은 호환 설정 보존에 사용하고, 콘텐츠는 전달받은 초안으로 전체 저장한다. `firestore.rules:105`에도 콘텐츠 revision 전진 조건이 없다.

**시나리오**: PC와 태블릿이 같은 워크아웃을 연다. PC에서 슬라이드를 추가하고 저장한 뒤, 태블릿의 이전 초안을 저장하면 PC 변경이 사라질 수 있다. 기존 재생 중 편집 잠금과는 별개의 문제다.

**제안**: 콘텐츠 revision과 `expectedRevision`을 추가한다. 충돌 시 초안을 유지하고 “최신 내용 확인 / 내 내용을 복사본으로 저장”을 제공한다. 첫 버전부터 자동 병합을 시도할 필요는 없다. 구버전 저장 허용 기간과 revision 도입 순서를 같이 정한다.

**완료 기준**: 동일 워크아웃의 서로 다른 초안 저장 시 두 번째 저장이 조용히 덮어쓰지 않음. 수정 도중 삭제된 워크아웃도 사용자 확인 없이 부활시키지 않음.

### C. 이미지 처리: 가장 우선적인 체감 속도 개선 후보

**근거**

- `slide_editor_screen.dart:373`: 이미지 선택에 크기·품질 제한 없이 전체 바이트를 읽어 `imageSource`로 만든다.
- `slide_editor_controller.dart:127`: 450ms 디바운스 임시저장. `slide_editor_repository_impl.dart:23`은 이미지 포함 모듈 전체를 JSON으로 만들고 `slide_editor_local_data_source.dart`가 SharedPreferences에 저장한다.
- `workout_storage_data_source.dart:14`: 신규 이미지 업로드는 모듈 순서대로 진행한다. URL로 저장된 기존 이미지는 재업로드하지 않는다.
- `workout_image_loader.dart:60`의 ResizeImage는 표시용 디코딩 경로다. 원본을 작은 파일로 업로드하는 처리는 아니다.

**제안 순서**

1. 이미지 선택 공통 경로에 크기·바이트 예산과 화면용 변환을 도입한다. 1080p·4K 결과는 실제 TV로 확인하고, 투명 PNG·GIF를 무조건 JPEG로 바꾸지 않는다.
2. 임시 이미지 바이트는 네이티브 파일/웹 Blob 저장소에 보관하고 초안에는 자산 참조만 기록한다. 복구·취소·정리 정책을 함께 만든다.
3. 저장은 2~3개 동시 업로드로 제한하고 순서를 보존한다. 이미 성공한 파일은 실패 재시도 때 재사용한다. 버튼에 “이미지 2/5 저장 중” 등 진행 상태를 표시한다.
4. 목록 썸네일은 원본 URL 재사용 대신 작은 파생 이미지 도입을 검토한다. 신규 데이터부터 적용하고 기존 파일은 별도 백필한다.

**완료 기준**: 이미지 5/30장 수업에서 입력 반응·저장 시간·최대 메모리·전송량의 전후 비교. 텍스트만 바꿀 때 큰 이미지 바이트를 다시 직렬화하지 않음. 앱 재시작 후 미저장 이미지 초안 복구 유지.

### D. TV가 실제로 준비됐는지 보여주기

**근거**: `workout_preflight_dialog.dart:68`은 컨트롤러에서 모듈 이미지를 준비하고 `:112`에서 시작 가능 여부를 계산한다. TV의 `display_mode_screen.dart:158` 이미지 준비와 `:187` 수신 revision 기록은 별도 비동기 효과다. 수신 확인이 이미지 완료를 기다리지 않는다. 이 준비 목록에는 공통 카운트다운 이미지가 포함되지 않는다.

**제안**: 기기별 `수신 / 준비 중 / 준비 완료 / 실패`를 세션 ID와 자산 버전에 묶는다. 재생에 필요한 첫 화면·카운트다운·다음 슬라이드를 우선 준비하고 나머지는 제한된 다운로드 큐로 처리한다. 명령 반영 revision과 준비 완료 revision을 분리한다. 운영자는 “TV 2/3대 준비, 1대 이미지 오류”를 보고 기다리기·재시도·해당 TV 제외를 선택한다.

**완료 기준**: 컨트롤러는 온라인이지만 TV의 이미지 요청만 실패한 상황에서 준비 완료로 오인하지 않음. 이전 세션의 늦은 응답이 새 세션의 준비 완료로 표시되지 않음. 전체 오프라인 재생 보장은 별도의 전체 자산 다운로드 완료 상태로 구분.

### E. 목록 동기화와 오프라인 준비를 분리

**근거**: `workout_firestore_data_source.dart:47`은 24개 단위로 전체 요약을 끝까지 읽는다. `workout_repository_impl.dart:61`은 이후 전체 요약을 대상으로 상세 캐시를 2개씩 예열한다. 상세가 최신 캐시에 있으면 서버 조회를 생략하지만 콜드 캐시에서는 전체 상세 조회가 발생할 수 있다. `:67`의 서버 오류는 캐시가 있으면 정상 목록으로 종료된다. `WorkoutController.refresh()`는 상위 상태에 오류가 없으면 이를 알아내지 못한다.

**제안**: 우선 목록의 데이터 상태와 동기화 상태를 분리해 `마지막 동기화 시각 / 캐시 사용 중 / 새로고침 실패`를 표시한다. 상세 다운로드는 오늘 예약·최근 사용·사용자가 지정한 “오프라인 보관”을 우선한다. 전체 검색과 폴더 개수 보존을 위해 당장은 경량 요약 전체 조회를 유지할 수 있다. 이후 실제 규모에 따라 서버 검색·진짜 페이지 로딩으로 확장한다.

**주의**: 문서 캐시가 있다는 이유만으로 이미지·공통 설정까지 오프라인 준비가 끝났다고 표시하면 안 된다. 기존 전체 오프라인 접근을 갑자기 없애지 않고 새 보관 정책으로 전환해야 한다.

**완료 기준**: 10/100/500개 워크아웃에서 첫 목록과 전체 동기화 시간을 별도 측정. 캐시 표시 중 서버 갱신 실패를 구분하고, 오프라인 준비 완료 수업은 앱 재시작·네트워크 차단 후에도 열리고 재생됨.

### F. TV는 자기 기기 상태만 구독

**근거**: `display_mode_screen.dart:64`가 전체 `displayDevicesProvider`를 보고 `:124`에서 자신을 찾는다. `device_pairing_realtime_data_source.dart:90`은 전체 devices 이벤트를 변환·정렬한다. 한 TV의 확인 기록 갱신이 다른 TV에도 불필요한 목록 처리를 일으킬 수 있다.

**제안**: 관리 컨트롤러는 전체 목록, TV는 `devices/{deviceId}` 단일 구독으로 분리한다. 연결 해제·소유 계정 변경·재구독 동작을 유지한다.

**완료 기준**: TV 1/3/10대에서 다른 TV 상태 변경이 자기 기기 DTO 변환과 화면 갱신을 유발하지 않음. 부모 onValue 이벤트가 발생한다고 전체 데이터가 매번 네트워크로 재전송된다고 단정하지 않는다.

### G. 배포 호환성과 자동 검증

**근거**

- `.github/workflows/firebase-hosting-merge.yml`은 테스트 후 규칙/Functions를 배포하고 그 다음 웹을 빌드한다. 따라서 웹 빌드가 실패해도 백엔드는 먼저 바뀔 수 있다.
- Android·iOS는 별도 워크플로이며 스토어 업로드 성공과 사용자 기기 업데이트는 다르다.
- `functions/package.json`의 기본 test는 `test/*.test.js`다. 별도 `*-emulator.mjs` 규칙·이관 검증은 현재 확인한 워크플로에서 실행하지 않는다. RTDB JSON 문법 검증은 권한 동작 검증을 대신하지 않는다.
- TV는 `playbackProtocol: 2`를 기록하지만 현재 기기 DTO에는 앱 버전·빌드·지원 설정 schema가 없다. 프로필의 앱 버전 표시는 이미 존재한다.

**제안**: 배포 가능한 산출물 생성까지 먼저 검증하고, 호환 가능한 백엔드를 배포한다. 규칙·이관 경로 변경 PR에는 demo 프로젝트 에뮬레이터 회귀를 추가한다. 기기 목록에 버전·빌드·프로토콜을 표시하고 파괴적 DB finalize는 운영 기기 호환 확인 후에만 실행한다. 컨트롤러도 확인 대상이다. 필요한 경우 구버전의 새 작업 시작을 제한하되 진행 중 수업 종료·제어는 유지한다.

**완료 기준**: 빌드 실패가 규칙 선배포로 이어지지 않음. 새 규칙+지원되는 구앱, 새 규칙+신앱 조합 검증. 업로드됨/스토어 처리 중/설치됨을 구별하고 롤백 절차를 기록.

### H. 장애와 속도를 측정할 수 있는 제품

**근거**: `lib/main.dart:33`에 네이티브 Crashlytics 오류 수집이 있고 `device_pairing_diagnostics.dart`는 페어링 실패 분류를 기록한다. 확인한 lib 경로에는 목록·저장·TV 준비·명령 반영의 단계별 성능 trace가 없다. 일부 재생·이미지 준비 실패는 debugPrint에만 남는다.

**제안**: `목록 최초 표시`, `상세 로딩`, `이미지 업로드`, `수업 시작`, `TV 준비`, `명령 반영`을 각각 계측한다. 웹에서도 같은 실패 분류를 기록할 경로를 둔다. 지원용 진단 복사는 버전·빌드·기기 모드·연결 상태·오류 코드와 최소한의 상관 ID만 포함하고 토큰·이메일·이미지 접근 URL은 제외한다. 다른 기기 간 지연은 시계 차이를 보정하거나 서버 확인 시점/기기 내 소요 시간을 나눠 기록한다.

**완료 기준**: “연결이 끊겼다”는 신고를 인증 만료·컨트롤러 연결·TV 연결·명령 충돌·이미지 실패로 구분할 수 있음. 최근 오류와 재시도 경로를 운영자가 확인할 수 있음.

### I. 라이브러리와 스타일의 계정 동기화

**근거**: `slide_templates_controller.dart` → `slide_editor_repository_impl.dart:30` → SharedPreferences 경로다. `slide_library_screen.dart:123`에도 “이 계정으로 이 기기에 저장한 슬라이드”라고 안내한다. 현재 버그가 아니라 명시된 로컬 기능이다.

**제품 제안**: PC에서 만들어 태블릿에서 사용하는 매장 흐름을 위해 계정 라이브러리로 확장한다. Firestore에 항목별 ID·revision을 두고 이미지는 공용 자산 참조를 사용한다. 기존 로컬 자료는 계정별 최초 가져오기·중복 방지·가져오기 확인을 거쳐 이전한다. 편집 중 임시 초안은 기기 로컬에 유지해도 된다.

**완료 기준**: 두 기기에서 추가·수정·삭제가 일관되게 반영되고, 재설치·기기 교체 후에도 라이브러리를 복구. 자동 덮어쓰기 대신 항목별 충돌 정책 적용.

### J. 리포트는 기록 범위와 실패를 포함해야 함

**근거**: `store_operations_realtime_data_source.dart:54`는 최근 1,000개 이벤트만 구독한다. `operations_metrics.dart:19`는 이 중 이번 달 재생 시작을 집계한다. `store_operations_screen.dart:661`의 예약 정시 시작 비율은 “실제로 시작한 예약”을 분모로 사용한다. 아예 시작하지 못한 예약은 이 비율에 포함되지 않는다. 접속 누적은 받은 이벤트 범위로 계산한다.

**제안**: 당장은 “조회된 기록 기준”과 기간을 표시해 전체 통계로 오인하지 않게 한다. A의 회차 상태를 기반으로 예정/성공/실패/취소를 구분하고 정시율의 분모를 정의한다. 월별 통계는 매장 시간대 기준 일별 집계+원본 이력 페이지로 분리하고 eventId로 집계 중복을 방지한다. 최다 수업은 이름 대신 workoutId로 집계한다.

**완료 기준**: 1,001개 이상 이벤트, 월 경계, 동일 이름 수업, 전혀 실행되지 않은 예약을 포함해 숫자의 의미와 실제 결과가 일치.

### K. 장기 비용과 유지보수

- **이미지 GC**: `workout_repository_impl.dart:178`은 공유 이미지 보호를 위해 문서만 삭제한다. 지금 즉시 파일 삭제를 붙이면 복사본·라이브러리·재생 스냅샷을 깨뜨릴 수 있다. 자산 참조 추적 → dry-run → 유예 기간 → 삭제 순서로 진행한다. 업로드 성공 후 문서 저장 실패로 남은 파일도 포함한다.
- **인덱스**: `firestore.indexes.json`의 fieldOverrides는 비어 있다. 쿼리하지 않는 큰 modules 필드의 인덱스 제외 후보를 조사한다. 운영의 실제 설정과 쿼리 사용 여부를 대조한 뒤 적용한다. Firebase도 조회에 쓰지 않는 큰 map/array의 인덱스 제외를 안내한다. [공식 지침](https://firebase.google.com/docs/firestore/best-practices)
- **리팩토링**: 슬라이드 편집 화면은 1,246줄, 매장 운영 화면은 905줄이다. 줄 수 자체는 속도 병목의 증거가 아니다. 기능을 수정할 때 이미지 선택/초안 저장/설정 섹션을 분리하고 Content·Preferences 경계를 지키는 방향이 적절하다. 분석만으로 화면 전체를 재작성하지 않는다.

## 5. 실행 권장 순서

1. **공통 계측 + 수업/데이터 보호**: H의 최소 계측을 넣고 A·B를 먼저 해결. G의 관련 규칙 검증을 함께 추가.
2. **체감 속도**: C의 이미지 입력·초안 참조화부터 진행. F의 단일 기기 구독은 독립적으로 적용 가능.
3. **현장 상태 표시**: D·E를 묶어 수업 준비, 재연결, 오프라인 여부를 일관되게 표시.
4. **기기 확대**: G의 버전/호환 관리와 I의 라이브러리 동기화.
5. **운영 누적 데이터**: J의 정확한 리포트, K의 자산·인덱스 정리.

계정 설정 DB의 파괴적 정리는 이 작업들의 선행 조건이 아니다. 기존 콘텐츠와 진행 중 수업을 보존하면서 각 변경을 독립 배포할 수 있어야 한다.
